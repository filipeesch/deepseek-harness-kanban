# Proposal

## Why

A deterministic stage cannot run on macOS whenever the session file policy is confined.
The isolated Bash guard proves that no owned process survived by sweeping the process
table with `ps -E`, but `/bin/ps` is setuid and `sandbox-exec` refuses to execute it
(`EPERM`). The guard therefore exits with status 125 before it prints its result
envelope, and the host can only report that the guard "did not return a valid result".
Every `tools.bash` call of a deterministic step fails this way, including the TypeScript
path, whose guard performs the same group inspection with `ps`. The only workaround is to
start the server with a broader file policy, which removes confinement from the very
scripts that are supposed to run under it.

The diagnostic half of this problem already landed: a guard diagnostic line is now
classified, persisted, and shown with its bounded facts. What is still missing is the
cleanup itself: the guard must deliver the script result and still prove that nothing it
started survives, on every supported system, without requiring broader permissions.

## What Changes

- The guard stops being a 240-line inline `node -e` source. It becomes a real bundled
  module (`lib/guard.mjs`) generated by the build from typed TypeScript modules composed
  through explicit interfaces, so its protocol, capture, completion, and cleanup paths can
  be read and unit-tested independently.
- Guard configuration moves out of process argv into a private `0600` file passed as a
  path. The HMAC authorization token and the reviewed script source no longer appear in
  the process command line, where any same-user process can read them.
- The invocation becomes shell-agnostic (`node "<guard.mjs>" "<config.json>"`) instead of
  the POSIX-only `command -v node` / `exec node -e '<source>'` wrapper.
- A new process-ownership port isolates "what is still alive and why". Each platform
  supplies one adapter: Linux reads `/proc`, macOS delegates the marker sweep to the host,
  Windows ships a job-object adapter that is not enabled yet.
- On macOS the host answers the marker sweep outside the confinement, over the
  authenticated lifetime channel that already exists. The guard reports that answer rather
  than reading a process table it cannot read. The already-reviewed freeze, re-check, and
  kill logic is reused instead of being reimplemented inside the sandbox.
- Every `ps` call made from inside the guard is removed. Process-group membership is
  proven with `pgrep -g` on macOS and from `/proc` on Linux, and group emptiness keeps
  using `kill(-pgid, 0)` until `ESRCH`.
- Windows keeps failing closed, and now also fails closed in watch mode: today the sweep
  returns early on `win32`, so a TypeScript execution reports clean without any proof.
  The job-object adapter exists as a seam only; the semantics of a Bash stage on Windows
  are decided separately.
- A confined file policy on Windows names the actual reason. The Windows backend reports
  partial file enforcement, so a stage is refused before the guard, and that refusal
  becomes an actionable configuration diagnostic instead of a generic one.
- The guard is excluded from its own sweep by its witness pid instead of by matching a
  literal string on the command line, which any user command could forge and which stops
  existing once the guard is a file.
- The duplicated stop/kill/re-check loop that exists in both the guard and the host is
  absorbed into the port, so one implementation serves both sides.
- **BREAKING** for local development only: the built artifact gains `lib/guard.mjs`, so a
  profile that loads a stale `lib` must rebuild before deterministic stages work.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `deterministic-steps`: process cleanup is proven by the readable process table that each
  platform actually offers, the guard reports its own reason when cleanup cannot be
  proven, and a platform without a supported ownership primitive fails closed in every
  execution mode rather than reporting a clean tree it never verified.

## Impact

- Host execution: `src/host/deterministic/` — the inline guard source is replaced by
  `guard/` modules and `process/` adapters; `lifetime.ts` gains a sweep action and a
  configuration file; `owned-processes.ts` is absorbed into the port; `guard-outcome.ts`
  gains the guard's own reason; `native-policy.ts` gains an actionable Windows refusal.
- Build: `scripts/build.mjs` emits `lib/guard.mjs`; `package.json` version is bumped in the
  same pull request, as required for an installed artifact.
- Documentation: `docs/deterministic-steps.md` describes the per-platform cleanup proof and
  stops claiming that the Windows guard is the only Windows limitation.
- Tests: a new native suite runs the real guard under the real confinement profile of the
  current system, which no existing test does today because every native deterministic test
  installs a `danger-full-access` policy. Linux bwrap/Landlock and Windows are not covered
  by automated evidence in this change and are recorded as accepted risk.
- No client, workflow YAML, board, or public API change. No change to the board that
  triggered this work.
