# Spec Delta

## MODIFIED Requirements

### Requirement: Published document content

The published layout SHALL consist of a hub manifest and one log per published board. The manifest SHALL carry a format version and one entry per board with a stable board key, the board name, the board order, and the board's project keys when the board allows only some projects. The order of the entries SHALL be the board order. A whole board workflow SHALL NOT appear in the manifest: each board's authored workflow text and its authored layout SHALL be carried only by that board's own log. A board that allows every project of its Hub SHALL publish no project keys for that board. A board that allows some projects SHALL publish exactly those project keys and SHALL be able to publish an empty set, which states that the board accepts no new task. Project keys in the published layout are identifiers only. The published layout SHALL NOT contain project records, project paths, Git roots, default branches, tasks, notes, conversations, worktrees, worktree base paths, or any other local setting. A board key SHALL be assigned when the board is first published, SHALL remain stable across board renames, and SHALL be unique within the manifest. A project key SHALL NOT be generated by publishing: a board SHALL publish the keys its projects already carry.

A published deterministic stage SHALL carry its authored language, exactly one inline code source or external file reference, directory selector, named exit routes, requested environment-variable names, and declared parameter names with their optional descriptions as workflow configuration. Parameter values SHALL NOT be published: a value is entry-local task data, not authored configuration. Publishing, checking, and applying that configuration SHALL NOT dereference a script file or publish the file contents captured for a local execution. The published layout SHALL NOT contain resolved local script paths, local credential references or values, executable trust decisions, execution identities, captured run configurations, process state, entry parameter values, or execution results. Local variable bindings SHALL remain isolated by local project and stable stage identity; publishing SHALL NOT turn them into project-wide or team-wide bindings.

#### Scenario: Publish the board list

- **WHEN** the user publishes a Hub with two boards
- **THEN** the manifest contains exactly those two boards in their board order
- **AND** each manifest entry carries its key, name, and project scope
- **AND** each board's own log carries that board's authored workflow

#### Scenario: Exclude local data

- **WHEN** a Hub with projects, tasks, notes, and conversations is published
- **THEN** none of those records or their identifiers appear in the published layout, except project keys named by a board's project keys

#### Scenario: A rename keeps the board key

- **WHEN** the user renames a published board and publishes the Hub manifest
- **THEN** the manifest entry keeps its existing key
- **AND** only the displayed name changes

#### Scenario: Preserve authored workflow text

- **WHEN** the user publishes a workflow containing comments and custom formatting
- **THEN** the published workflow text inside that board's log matches the authored text without normalization

#### Scenario: Publish a board that allows some projects

- **WHEN** the user publishes a board restricted to two projects
- **THEN** that board's manifest entry carries the two project keys
- **AND** no project path or project record appears in the published layout

#### Scenario: Publish a board that allows every project

- **WHEN** the user publishes a board with no project restriction
- **THEN** that board's manifest entry carries no project keys

#### Scenario: Publish a closed board

- **WHEN** the user publishes a board restricted to no project
- **THEN** that board's manifest entry states an empty project key set
- **AND** a receiving installation presents that board as closed for creation

#### Scenario: Publish a deterministic definition without its local authority

- **WHEN** a deterministic stage has inline code, named exit routes, requested variable names, declared parameter names, locally trusted executable code, and local variable bindings
- **THEN** its board log carries the authored deterministic definition, the requested names, and the declared parameter names and descriptions
- **AND** no trust decision, credential reference, credential value, run record, entry parameter value, or project-local binding appears in the published layout

#### Scenario: Publish a file reference without resolving its local contents

- **WHEN** a deterministic stage references an external file and a local run has captured that file
- **THEN** the board log carries the authored file reference
- **AND** publishing does not read or embed the referenced file, its resolved local path, or the run snapshot

#### Scenario: Publish parameter declarations without values

- **WHEN** a deterministic stage declares a pipeline and an app parameter and a local task entry holds values for them
- **THEN** the board log carries the two declarations with their descriptions
- **AND** neither the entry's values nor any other local value appears in the published layout

### Requirement: Board event log content

Each published board SHALL have one log that carries the board's published workflow as a snapshot together with a tail of events appended after that snapshot. The snapshot SHALL carry the board's authored workflow text, so the authored text and its formatting are recovered exactly, and the stable stage identity of every stage it names. An event SHALL carry the kind of change, the format version of that event, a sequence number that orders it within the board's log, the moment it happened, and, when it addresses a stage, the stable stage identity it addresses.

The event vocabulary SHALL distinguish, at least: the board workflow being created or replaced as a whole, a change to a workflow-level field, a change to the initial stage, a stage being created, a change to one stage field, a change to a stage identifier, a stage being removed, a change to a stage's stored layout, a stage group being created, changed, or removed, and a connection layout being set or removed. A change that alters only stored layout SHALL be coalesced so that one user gesture produces one event. A change to a stage identifier SHALL be one event that names the stable identity and the new identifier; it SHALL NOT be expressible as a removal followed by a creation.

The log SHALL be compacted: when the tail grows past the supported bound, the tail SHALL be folded into a new snapshot and the folded events SHALL be dropped. A member whose stored sequence for a board is older than the retained snapshot SHALL re-establish that board from the snapshot, and that recovery SHALL NOT lose the stage identity of a stage the snapshot names. The published layout SHALL be recoverable without replaying the whole history of a board.

An event whose kind or format version this installation does not know SHALL NOT be skipped silently. It SHALL stop that board's cursor at that event, SHALL be reported as a board that requires a plugin update, and SHALL NOT prevent another board from being applied.

The snapshot and event vocabulary SHALL represent a deterministic stage's complete authored definition, including its language, inline code or file reference, directory selection, named exit routes, requested environment-variable names, and declared parameter names with their optional descriptions. A parameter value SHALL NOT be represented, because a value is entry-local task data. Creation, replacement, edits, clearing deterministic configuration, and switching between conventional and deterministic configuration SHALL recover the same valid workflow that was published. Definition changes SHALL be represented without publishing local execution authority, entry parameter values, or runtime records. Inline source text and external file references SHALL retain their authored meaning and untouched YAML formatting through event application and snapshot compaction. Retained historical events SHALL keep their original sequence, time, and format-version stamps when new events or a newer supported envelope are written; compaction SHALL fold events into the snapshot rather than relabeling their historical stamps.

#### Scenario: Recover a board from its snapshot and tail

- **WHEN** a member reads a board's log for the first time
- **THEN** it reads the snapshot and the events after it
- **AND** the resulting workflow equals the workflow the publisher held

#### Scenario: Preserve authored workflow text through the log

- **WHEN** a board's log carries a workflow with comments and a custom key order
- **THEN** the recovered authored text matches it exactly

#### Scenario: A rename is one event

- **WHEN** the team renames a stage identifier
- **THEN** the board's log gains one event naming the stable identity and the new identifier
- **AND** no event removes the stage

#### Scenario: One gesture produces one layout event

- **WHEN** the user moves or resizes a stage
- **THEN** the board's log gains one layout event describing the result
- **AND** it does not gain one event per intermediate position

#### Scenario: Compact the tail

- **WHEN** a board's tail grows past the supported bound
- **THEN** the tail is folded into a new snapshot
- **AND** the folded events are dropped
- **AND** the recovered workflow is unchanged

#### Scenario: A member behind the retained window recovers

- **WHEN** a member's stored sequence for a board is older than the retained snapshot
- **THEN** the board is re-established from the snapshot
- **AND** no stage loses its stable identity

#### Scenario: An unknown event stops only its board

- **WHEN** a board's log contains an event whose kind or version this installation does not know
- **THEN** that board's cursor stops at that event and the board reports that the plugin must be updated
- **AND** another board remains applicable

#### Scenario: Recover deterministic configuration from creation and edits

- **WHEN** a board log creates a deterministic stage and later changes its source, directory, requested variable names, declared parameter names, or exit routes
- **THEN** replay recovers the complete resulting deterministic definition
- **AND** the log contains no local trust, credential bindings or values, entry parameter values, or run state

#### Scenario: Compact inline source and external references without losing them

- **WHEN** a log containing inline TypeScript or Bash and another stage's external script reference is compacted
- **THEN** recovery from its snapshot retains both authored definitions, their stage identities, their declared parameter names, and their exit routes
- **AND** source strings and untouched comments, quoting, and key order are preserved

#### Scenario: Append new grammar without rewriting old event stamps

- **WHEN** a supported legacy log gains deterministic configuration under a compatible upgraded envelope
- **THEN** retained earlier events keep their sequence numbers, timestamps, and original event format versions
- **AND** newly appended events state the format they actually use

#### Scenario: Clear deterministic configuration without retaining executable behavior

- **WHEN** a published stage is changed from deterministic configuration to a valid conventional stage
- **THEN** replay and recovery from a compacted snapshot both produce that conventional configuration
- **AND** no deterministic definition is retained by an omitted-field or partial-event fallback

#### Scenario: Recover parameter declarations without values

- **WHEN** a log creates a deterministic stage that declares parameters and later edits those declarations
- **THEN** replay and recovery from a compacted snapshot retain the latest declared names and descriptions
- **AND** no entry parameter value is recovered from the log

### Requirement: Published document version negotiation

Reading the published configuration SHALL compare its format version with the versions this installation supports. The current format version SHALL be 3. A version 1 or version 2 published configuration, which carries whole board workflows in one document, SHALL be read and normalized to the current format: each of its boards SHALL become a manifest entry together with a board log whose initial state is that board's authored workflow, and each stage SHALL receive a stable stage identity derived from the authored identifier, so that a later rename is still distinguishable from a replacement. Such a configuration SHALL NOT be rejected, and the stored publishing state SHALL be normalized the same way when it is loaded, so an installation that already published keeps its bindings, its orphan records, and its recorded removals. A configuration whose format version is newer than this installation supports SHALL NOT be applied and SHALL NOT be published over, because its shape is unknown and writing it would drop content this installation cannot represent. In that state the installation SHALL keep its local edits, SHALL keep the Hub's publishing binding, and SHALL present a warning that the plugin must be updated. The warning SHALL be presented in the Team Settings panel and in the Hub's publishing status. The state SHALL clear without user action once a plugin that supports that version reads the configuration. An individual board log written by a newer plugin SHALL be treated the same way for that board alone: the board SHALL report that the plugin must be updated, SHALL NOT be applied, SHALL NOT be published over, and SHALL NOT prevent another board from being applied or published.

Board logs SHALL negotiate their own envelope version independently of the manifest. A log containing deterministic stage configuration SHALL declare a supported envelope that distinguishes its workflow grammar from earlier logs before its snapshot is interpreted. The current board-log envelope SHALL be 3. A log whose snapshot or events declare a parameter name SHALL state envelope 3, because a reader that supports only envelope 2 cannot represent that declaration. Such a reader SHALL report that the affected board requires a plugin update and SHALL NOT treat the log as invalid, as a conventional workflow, or as a destination for publishing over. This compatibility signal SHALL be present for a newly published snapshot with no events and SHALL survive compaction. A reader that does not support the envelope SHALL report that the affected board requires a plugin update rather than treating the workflow as a conventional stage or an invalid generic workflow. The current reader SHALL continue to read supported legacy board logs; merely reading them SHALL preserve retained event stamps and their content heads. An envelope upgrade SHALL NOT silently restamp retained historical events.

#### Scenario: Read a version 1 document

- **WHEN** the installation reads a published configuration written with format version 1
- **THEN** it reads the boards with no project keys
- **AND** no board is presented as restricted

#### Scenario: Read a version 2 configuration

- **WHEN** the installation reads a published configuration written with format version 2
- **THEN** each of its boards becomes a manifest entry with a board log carrying that board's authored workflow
- **AND** every stage receives a stable stage identity derived from its authored identifier
- **AND** the team is not required to republish

#### Scenario: Normalize stored version 1 state

- **WHEN** the installation loads publishing state whose stored documents use format version 1
- **THEN** the state is normalized and retained
- **AND** its board bindings, orphan records, and recorded removals are kept

#### Scenario: Refuse to apply a newer document

- **WHEN** the installation reads a published configuration whose format version is newer than it supports
- **THEN** no team change is applied
- **AND** the local Hub is unchanged

#### Scenario: Refuse to publish over a newer document

- **WHEN** the published configuration uses a newer format version and the user asks to publish
- **THEN** nothing is written to the team storage
- **AND** the local change is kept as a draft

#### Scenario: Isolate a newer board log

- **WHEN** one board's log was written by a newer plugin version
- **THEN** that board reports that the plugin must be updated and is neither applied nor published over
- **AND** every other board remains applicable and publishable

#### Scenario: Warn that the plugin must be updated

- **WHEN** the published configuration uses a newer format version
- **THEN** the Team Settings panel presents a warning that the plugin must be updated
- **AND** the Hub's publishing status presents the same state

#### Scenario: Clear the warning after an update

- **WHEN** a plugin that supports the published configuration's version reads it
- **THEN** the warning is no longer presented
- **AND** checking and publishing proceed normally

#### Scenario: Read a supported legacy board log

- **WHEN** an installation supporting deterministic stages reads a board log in the previously supported envelope
- **THEN** the board remains readable with the same authored workflow and stage identities
- **AND** a read without a publication or compaction preserves retained event stamps and the content head

#### Scenario: Detect unsupported executable grammar in an initial snapshot

- **WHEN** a reader encounters a deterministic board snapshot in an envelope it does not support and the log has no events
- **THEN** the affected board reports that a plugin update is required before interpreting the snapshot
- **AND** it is neither applied nor published over
- **AND** another supported board remains applicable and publishable

#### Scenario: Detect an unsupported parameter declaration

- **WHEN** a reader that supports only envelope 2 encounters a board log whose workflow declares a parameter name
- **THEN** that board reports that a plugin update is required
- **AND** the log is neither interpreted as an invalid workflow nor published over
- **AND** another supported board remains applicable and publishable

#### Scenario: Compaction preserves the compatibility boundary

- **WHEN** deterministic events have been folded into a board snapshot and removed from the tail
- **THEN** the resulting log retains the envelope compatibility signal for deterministic configuration
- **AND** a reader that does not support it still reports that the affected board requires a plugin update

### Requirement: Shared executable configuration carries no local authorization

A shared deterministic definition SHALL NOT grant execution authority to its receiving installation. Saving, publishing, first-connection adoption, applying team updates, and recovery from a board snapshot SHALL NOT create executable trust, local variable bindings, or entry parameter values. Local variable values SHALL remain in the native credential mechanism under their local project-and-stable-stage scope; neither values nor local credential references SHALL be copied through the published layout. A published declaration SHALL NOT carry parameter values; receiving a declaration SHALL NOT create, inherit, or expose a value, and a value SHALL remain bound to the local entry that holds it. Receiving a definition SHALL NOT revoke unrelated local trust or bindings. A stage whose current entry has not been explicitly started SHALL NOT begin a program merely because a received workflow adds or changes its deterministic configuration. Starting a new entry or an explicit Play SHALL still require the local authorization and the entry's own values defined for deterministic steps.

#### Scenario: A teammate's approval does not authorize local execution

- **WHEN** an installation receives a deterministic stage whose executable version another installation has trusted
- **THEN** receiving the workflow conveys no local trust decision
- **AND** execution remains subject to the receiving installation's own authorization

#### Scenario: Snapshot recovery does not restore another member's secrets

- **WHEN** a member reconstructs a deterministic board from its published snapshot and tail
- **THEN** no local credential binding, credential value, executable trust record, entry parameter value, or active run is reconstructed from that layout
- **AND** existing unrelated local bindings and trust remain unchanged

#### Scenario: Receiving a definition does not manufacture a stage entry

- **WHEN** an existing local task remains in its stage while a team update makes that stage deterministic
- **THEN** applying the configuration does not start a script or create a new task-stage entry
- **AND** the user can explicitly Play the stage subject to local authorization and the entry's own parameter values

#### Scenario: A received declaration carries no values

- **WHEN** an installation receives a deterministic definition that declares a pipeline and an app parameter
- **THEN** the receiving installation stores the declaration without any parameter value
- **AND** an entry created there fails for the missing values until the origin declaration or the local repair supplies them
