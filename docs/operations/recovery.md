# Recovery

This document covers a failed or partial operation, a durable record that needs a decision, and the recovery paths for team sharing. It is not authorization to widen native policy, edit a profile, repair host data, or delete user content.

## Failed or partial worktree operations

[The coordinator](<../../src/host/worktrees.ts>) journals requested intent, canonical target, prior per-session directories, completed switches, Git completion, archived session IDs, and failure details in durable task metadata. Git, native sessions, and metadata do not form one transaction. A failed response can follow a real external effect.

1. Open the affected card. The drawer-wide status above the tabs shows the operation kind, phase, target, and what completed. Do not infer that every tab moved from one successful switch or from the card's last committed cwd.
2. **Waiting** means all associated chats must become idle, including closed tabs and known turns, pending native interactions, jobs, descendants, and schedules. Waiting resumes on native activity events and startup; cleanup does not automatically cancel agents or owned work. Resolve the actual native activity deliberately, then use the kind-specific **Retry** action if needed.
3. During active context work, plugin admission of new chats and runs is gated and activity is rechecked before individual switches. Native actions can still race checks; there is no global idle lease. Do not send work into a mixed or unresolved context.
4. On **failed**, address the reported condition and choose the kind-specific **Retry** action to resume the recorded intent. A failed creation is settled from two recorded facts rather than from the directory alone: the destination (absent, empty, or present) and its worktree registration (none, orphan, or registered). An attempt whose destination no longer exists protects nothing, so the host releases it, and an orphan registration whose directory is gone is cleared by targeting that exact path; retry, return, and deletion then work again, including for a journal recorded before this behavior existed.
5. A destination that exists without a registration is named as an incomplete checkout: it is never adopted, and **Discard incomplete checkout and retry** removes it after explicit consent, clears that registration, removes the empty directories above it up to but never including the configured worktree base, and retries the same creation in one accepted action.
6. A registered checkout is recovered by inspection only when its branch matches the recorded attempt; a checkout Git does not register becomes an unclaimed diagnostic on return. Create recovery requires the persisted, operation-bound absent-target precondition plus the exact canonical repository, path, and local-branch match; merely finding an existing matching checkout is not ownership proof. A retry reuses the branch a failed attempt left only when its tip is the commit the attempt proved; a moved tip is refused instead of being reset or deleted.
7. A `SHARED_WORKTREE` failure offers the consented **Force remove checkout** action, which lists every blocking task and native conversation and removes the checkout after an explicit opt-in; it bypasses only the sharing guard. Policy denials, dirty-check discard consent, idleness, and the refusal to force while another task operates on the same checkout are never bypassed. Other failures are not instructions to broaden access.

**Return chats to project** cancels a pending confirmed transition and coordinates all retained conversations back to the exact base project path. This is not rollback of external side effects: it retains a verified created or attached checkout and binding for explicit later management while base becomes the active cwd; it does not delete the checkout or branch. A legacy, interrupted detached or mismatched-ref checkout can instead be recorded as diagnostic-only **Unclaimed worktrees**, without replacing a distinct known binding.

If native conversation archiving has begun during task deletion, return is hidden or refused with `DELETE_IN_PROGRESS`. Use the deletion-specific **Retry deletion** action after resolving the failure. The plugin cannot silently unarchive chats or recreate a removed checkout.

**Deadlines and cancellation:** reference reads keep a short deadline, while a command that creates, removes, or reads a checkout's working tree runs under its own long deadline, so a large repository is not killed mid-checkout. While such a command runs, the drawer status offers **Cancel checkout**; cancelling aborts only that operation and records `OPERATION_CANCELLED` with the same recovery actions as any other failure. It does not delete a branch, reset a registration, or report the work as completed, and a cancelled checkout that left files is recovered through the same discard route.

**Unclaimed worktrees are read-only diagnostics**, never ownership, active context, or a removal target. The Git notice lists path, branch, and reason with no automatic attach or remove and no prefilled destructive target. Inspect with Git and choose a separate explicit attach if appropriate; a successful attach clears the matching diagnostic. Task deletion leaves unclaimed checkout files on disk and warns about them.

**Branch modes:** discovery and Existing branch accept only supported local heads. A remote ref may be entered as the source of a New branch, which creates an attached local branch. Remote-only existing selections fail before checkout creation; do not retry them as if detached HEAD were supported existing-branch recovery.

Failed operations remain recorded for explicit recovery; nonfailed recorded work is reconsidered on restart. If a durable write itself failed, external state may be ahead of metadata. Preserve the error and inspect the known target before retrying; do not delete the journal or erase native logs to clear the UI.

A Hub written by this release can carry a creation attempt's recorded source commit, its observed destination, and the branch-reuse fact. A build older than the release that introduced that record rejects the Hub, so retry or return the affected task to base before downgrading.

## Card instructions and timed sends

The card **play** action and the timed send both use the same host command. [The host command path](<../../src/host/app.ts>) requires the task to still be in that stage, no unresolved context operation or confirmed transition, the exact unresolved entry identity, and an exact match with the expected raw instruction. A missing, replaced, or changed entry produces `INSTRUCTION_ALREADY_RESOLVED` or `INSTRUCTION_CHANGED`; review the current instruction rather than silently running a replacement. The host sends the instruction to the task's first open conversation, followed by the transition briefing when the stage configures two or more targets, creating one when none is open, after canonical context admission. It does not move the task, does not offer a conversation picker, and does not persist a confirmed transition. Admission failures surface inline on the card and in the drawer; inspect the conversation before retrying, because a retry is a new send.

The drawer shows waiting, sending, and failed status above the tabs. Once context is ready, the kind-specific **Retry** action resumes the saved choice; **Return chats to project** clears it when prompt admission is not in progress. A stage may already have changed when native prompt admission fails, so check both stage and status rather than interpreting the error as a complete rollback.

## Auto mode recovery

Every turn ending that is not `completed` (`error`, `blocked`, `aborted`, `max-tokens`) records a pause with the matching reason, and no advance is admitted, for a task whose auto mode is enabled. The pause survives reloads and restarts and is cleared by an admitted advance, by disabling auto mode, or by any move of the task. Reading a conversation does not clear it.

An admission failure that happened before a durable transition records `advance-failed`; a declaration whose target a workflow edit removed records `transition-stale`. Those records exist only for a task whose auto mode is enabled; a task whose auto mode is disabled records no pause and keeps its declaration for the next completed turn.

An admitted transition that fails is reported through its transition state, keeps auto mode enabled, and is not retried automatically. The destination entry stays unresolved, so the card play action remains available; sending that instruction clears the failed record, and the drawer also offers an explicit retry or a dismiss of the failed record.

Any change to the setting forgets a turn that has not settled yet, so re-enabling or resuming within the settle window does not advance for a turn that ended before the change. Activating the **Auto** chip resumes any recorded pause; it turns the setting off only when nothing is recorded. `resume_task` clears the pause without enabling a disabled task, moving the card, or advancing a turn that already ended. Sending a prompt does not resume a paused task.

The record lives inside the task's auto-mode field of the local Hub document. Tasks are never published to a shared Hub document, so only this installation's own stored data can be affected.

### Downgrade preparation

Before selecting an older plugin build, resume every paused task, clear every declared transition, and stop every active script. The pause record and the declaration's reason live in the local Hub document, and a build older than the release that introduced them rejects the Hub instead of reading it. [Scripted steps](../user/scripted-steps.md) owns the scripted-state rollback.

## Legacy confirmed transitions

Legacy confirmed-transition records remain readable and retryable in the drawer. Once legacy context is ready, **Retry confirmed action** resumes the saved choice; **Cancel action and return to base** clears it when prompt admission is not in progress. The current UI does not create these records.

The legacy path requires equality with the exact raw instruction displayed for approval before creating a new conversation, performing Git work, or journaling the move. A missing or changed instruction produces `INSTRUCTION_CHANGED`; review the current instruction rather than silently approving a replacement. Once admitted, the destination, chosen conversation, captured approved text, placement anchor, and stable native request ID are persisted; waiting or retry does not substitute a newer workflow instruction.

A transition does not create or prompt for a worktree; use the notice or the Git section instead. The notice's **Create worktree** uses the displayed derived branch, destination, and source directly; it refreshes collision-aware defaults when untouched, routes to Git when no destination is configured, and keeps a Git failure inline with a review path. **Move only** never submits a prompt. **Move and run** queues the instruction into only the selected native conversation; other chats are not messaged.

For a legacy confirmed transition, an interrupted admission with `DELIVERY_UNCERTAIN` requires an explicit retry using the **same** native request identity; native deduplication protects that request. Admission uses native queue mode: it is not proof the turn started, finished, or succeeded. Do not manually send the legacy instruction again just because a waiting or uncertain status is visible, and do not change targets while admission is in progress.

## Deletions and removals

Confirmed task deletions and worktree-only removals are admitted from persisted state only: the host verifies that the task exists, that its recorded worktree binding still matches the confirmed target, and that no other context operation holds it. Admission intentionally runs no Git command, native conversation read, or filesystem scan, so the command returns immediately and the board stays usable.

Execution happens in a background lane per repository: at most one destructive operation runs in a repository, while operations on different repositories proceed concurrently. Each lane begins with the authoritative preflight — conversation idleness, canonical target stability, checkout sharing, and local-change detection — evaluated once per execution over the repository facts the operation resolved once. It then returns conversations to base, and from that point removes the checkout and archives native histories concurrently, so the card leaves the board only after both finish. The checkout removal re-evaluates the sharing refusal immediately before the Git command, because the host can report a new user of the checkout at any moment.

The operation carries a persisted **queued** phase before execution. A preflight failure is recorded on the task with its failing phase and published to the card, the board notice, and the drawer status, where retry, return, force, and the separate discard consent recover it; a busy conversation moves the operation to **waiting** and it resumes on the next native activity event. The board notice also reports retained plain-checkout paths. A queued or in-progress operation resumes after a plugin restart, and shutting the plugin down does not discard its journal.

## Team sharing recovery

A shared Hub keeps its state in its own storage domain. A Git binding also owns a managed clone under `DSH_HOME/kanban/shared/<hubId>`; a Google Drive binding owns provider state (`fileId`, `headRevisionId`, `changesPageToken`, `driveId`) and keeps the document in the selected Drive folder; a local folder binding owns the observation (`mtimeMs`, `size`) of the document it reads. Google Drive tokens live in the host credential store (a 0600 file, not an OS keychain, readable by same-user processes). The OAuth callback uses a loopback port on the host, so the browser must run on the same machine as DSH; a remote browser cannot complete the connection.

- **A board written by a newer plugin version** (`SHARING_DOCUMENT_VERSION_UNSUPPORTED`) is a per-board state: that board is neither applied nor published over, its Team Settings row says **Plugin update required**, and every other board of the Hub keeps checking, applying, and publishing. Updating the plugin clears the state without any action on the board. Descriptions, decision gates, and a board's default preset travel this way whenever a board publishes them; a board that carries none of them keeps the event format an older installation still reads.
- **Unreachable storage** is reported as `Updates unavailable` with the last successful check time. Local editing and task work continue; the next scheduled check retries. Git checks report their typed failure instead of hanging because terminal prompts are disabled for plugin-owned commands; Google Drive checks retry on the next interval and keep local changes pending.
- **A Git publish that loses a race** is refused with `SHARING_STALE_TOKEN`, publishes nothing, and refreshes the seen document so the interface shows the team updates. Run **Get updates**, resolve any review, then publish again.
- **A Google Drive or local folder write that loses a race** is detected before or after the write (`SHARING_STALE_TOKEN` or `SHARING_CONCURRENT_WRITE`), is not reported as success, and keeps local changes pending. Review the team changes; the previous document remains in the Drive revision history or in the desktop client's own history. Neither storage has an atomic conditional write, so the plugin never promises one.
- **A missing team document** is not treated as "the team removed every board". If the storage was readable before and the layout stamp disappears, the check reports `SHARING_DOCUMENT_MISSING` and leaves the local and received documents untouched.
- **A local folder is unavailable** is reported as `SHARING_FOLDER_MISSING`, `SHARING_FOLDER_NOT_DIRECTORY`, or `SHARING_FOLDER_UNWRITABLE` while local changes stay pending. Restore the folder — remount the drive, resume the desktop client, or fix the permissions — and the next check resumes without a new binding. The document is never recreated silently after it disappears.
- **A folder cannot be connected** names its condition: `SHARING_FOLDER_MISSING`, `SHARING_FOLDER_NOT_DIRECTORY`, `SHARING_FOLDER_UNWRITABLE`, `SHARING_FOLDER_RESERVED` for a directory inside the plugin's managed publishing workspace, or `SHARING_ADDRESS_IN_USE` for a folder another Hub already binds. Only the suggested `~/.dsh-kanban/<hubId>` path is created on connect; any other path is the user's to create.
- **A synchronization conflict copy** (`SHARING_CONFLICT_COPY`) is listed by name, blocks automatic apply and publish, and is never merged, renamed, deleted, or preferred. Decide which version is current, copy it over the same file the copy came from — the layout stamp `kanban-hub.yaml`, or the corresponding board log `kanban-boards/<key>.jsonl` — remove or rename the other copies (Dropbox's `(conflicted copy)`, Drive's `(1)`, OneDrive's `-MACHINE`), and the next check clears the review.
- **A refused update** (`SHARING_REFUSED`) applies nothing. Resolve the named boards, columns, and tasks locally — move the tasks, rename the unpublished board, or delete the empty board — and run the sync again. The interface deliberately offers no override.
- **Authorization is lost or the account changes** (`SHARING_RECONNECT_REQUIRED`, `SHARING_AUTH_DENIED`, `SHARING_AUTH_POLICY`): reconnect the Google account. Local boards, workflows, and pending changes are kept; bindings that the new account cannot access are reported.
- **A corrupt sharing record** is quarantined with `SHARING_STORAGE_INVALID` and ignored at startup, so the Hub domain and the board keep working. Reconnecting the Hub recreates a clean record; local boards are untouched.
- **Disconnecting** removes the binding and any managed Git clone; reconnecting creates a new clone, rebinds a Drive folder, or binds the same local folder again. Deleting a published Hub removes its binding and managed workspace but leaves the team document, the bound local folder and every file in it, and the Google account authorization untouched. A plugin uninstall can leave a managed clone behind; it is safe to delete after confirming the Hub is no longer published in any installation.
- **Google Cloud prerequisites** are external: the OAuth client must be a Desktop app, the consent screen must include `openid`, `email`, `profile`, and the Drive scope, and a published External app needs Google's restricted-scope verification before accounts outside its test list can authorize. Testing mode limits refresh tokens to seven days. The default client id and no-secret exchange are only exercised by the manual acceptance run, not by CI.

**Rollback** to a plugin version that only understands the v1 sharing record presents migrated Git Hubs as unpublished (`SHARING_STORAGE_INVALID` on open). Every local board, workflow, task, and note is retained; reconnect the Hub to restore the binding from the team document. Disconnect Google Drive bindings before downgrading so the old version does not attempt to read Drive state. A local folder binding presents the same quarantine on a version that does not know the storage; the folder and its layout stamp are untouched, so reconnecting on the newer version restores the binding.

## Unreadable conversation

A task conversation whose Session log cannot be read reports the state on its card and inside the conversation; what the person sees and the actions available are in [conversations](../user/conversations.md#unreadable-conversation).

Repair is bounded to one corruption class: a repeated PTC dispatch identifier. It renames only an identifier that already started earlier, follows every record that references it, including a job that settles after the invocation closed, and leaves every other record and payload untouched.

The rewritten artifact is validated with the installed loader's chain before anything is written. The original is copied under `session-repair-backups/kanban/<session id>/<timestamp>/` inside the harness home, the replacement is an atomic rename, and a repair the host still rejects restores the original only when the bytes on disk are the ones the repair installed.

The final replacement is not a compare-and-swap: another process that rewrites the log at that instant is outside the plugin's control. A repair refuses every change it can observe and never overwrites bytes it did not write.

## Metadata, disabling, and rollback

The plugin uses the native storage-domain service's namespaced **kanban** domain, version **1**, single snapshot; see [the adapter](<../../src/host/storage.ts>) and [validated durable store](<../../src/domain/store.ts>). It stores projects, workflows, tasks, notes, and operation references, not a second transcript database. Mutations are serialized, revision checked where supplied, and published after durable writes. One active host and profile writer is the supported boundary; there is no multi-host replication guarantee.

Use the correct host and profile's supported backup procedure before an upgrade or manual recovery, including both plugin metadata and native session storage as needed. The physical backing path belongs to that host configuration; do not guess it from cwd. This plugin provides no general backup, restore, or export UI. Unsupported schema versions fail rather than silently reset; preserve the original snapshot and use compatible code or a reviewed migration, not a blank-state overwrite.

Disabling or uninstalling through native plugin management removes plugin UI, tools, and listeners and releases its UI session references. It does not delete tasks, native histories, branches, worktrees, or stored metadata. A compatible re-enable can reconnect the same native IDs. Reverting plugin code does not undo confirmed checkout deletion or native-chat archiving. Do not use source, core, or profile edits to disguise partial cleanup.

## Questions, notes, and stale views

A stream failure keeps the last board state; **Retry updates** restarts the live feed, an initial load failure uses **Retry loading board**, and a failed question round uses **Retry questions**. A rejected command is reported by the surface that started it, not by the board-update status.

Creation commands return a transient exact entity receipt. When the receipt is missing or the created entity is unavailable, inspect or refresh and select the saved entity explicitly before another creation; the UI does not infer it from a snapshot. [Conversations](../user/conversations.md) owns the question, draft, dismissal, and stale-view behavior.
