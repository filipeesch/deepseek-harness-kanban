# hub-sharing Specification

## Purpose

Let a team keep a Hub's boards and workflows aligned through an optional, storage-agnostic publishing channel, while projects, tasks, notes, and Hub names stay local to each installation.

## Requirements

### Requirement: Optional publishing per Hub

Publishing SHALL be opt-in for each Hub and SHALL bind that Hub to exactly one storage: a Git repository, a Google Drive Cloud folder, a Google Drive Local folder, or a local folder. A Hub that has not been published SHALL have no storage binding, managed local workspace, scheduled check, or publishing state, and every existing board, workflow, and task behavior SHALL remain unchanged. Enabling publishing SHALL require a valid binding for the chosen storage: a Git binding SHALL create a plugin-managed local clone of the repository, a Google Drive Cloud binding SHALL use the selected folder and its `kanban-hub.yaml` document, a Google Drive Local binding SHALL use the selected folder inside a discovered Google Drive location and its `kanban-hub.yaml` document, and a local folder binding SHALL use the selected directory and its `kanban-hub.yaml` document. Disabling publishing SHALL remove the binding and any plugin-managed local workspace, SHALL stop automatic checks, and SHALL retain every local board, workflow, task, note, project, conversation, and worktree. Disabling publishing SHALL NOT remove the team's shared document, the Google account authorization that other Hubs may use, the Google Drive for desktop installation or its local cache, or the bound folder, its document, or the `team-files` directory.

#### Scenario: Unpublished Hub keeps current behavior

- **WHEN** a Hub has never been published
- **THEN** its boards, workflows, and tasks behave exactly as they did before this capability existed
- **AND** no binding, managed local workspace, scheduled check, or publishing state exists for that Hub

#### Scenario: Enable publishing

- **WHEN** the user enables publishing for a Hub with a valid repository address
- **THEN** the plugin creates a managed local clone of that repository
- **AND** Team Settings presents the Hub as connected

#### Scenario: Enable Google Drive publishing

- **WHEN** the user enables publishing for a Hub with a connected Google account and a selected folder
- **THEN** the plugin creates or adopts the `kanban-hub.yaml` document in that folder
- **AND** Team Settings presents the Hub as connected

#### Scenario: Enable Google Drive Local publishing

- **WHEN** the user enables publishing for a Hub with a folder selected inside a discovered Google Drive location
- **THEN** the plugin creates or adopts the `kanban-hub.yaml` document in that folder
- **AND** Team Settings presents the Hub as connected
- **AND** no account authorization is requested

#### Scenario: Enable local folder publishing

- **WHEN** the user enables publishing for a Hub with an existing writable directory
- **THEN** the plugin creates or adopts the `kanban-hub.yaml` document in that directory
- **AND** Team Settings presents the Hub as connected
- **AND** no managed local workspace is created

#### Scenario: Disable publishing

- **WHEN** the user disables publishing for a Hub
- **THEN** the binding and any plugin-managed local workspace are removed
- **AND** every local board, workflow, task, note, project, conversation, and worktree remains
- **AND** the team's shared document is unchanged

#### Scenario: Keep the team files directory on disable

- **WHEN** the user disables publishing for a Hub whose storage holds a team files directory
- **THEN** the binding and any plugin-managed local workspace are removed
- **AND** the team files directory and every file in it remain unchanged

### Requirement: Published document content
The published document SHALL contain a format version and one entry per board with a stable board key, the board name, the board order, the board's workflow YAML exactly as authored, and the board's project keys when the board allows only some projects. The format version SHALL be 2; a version 1 document SHALL be read and normalized as defined by Published document version negotiation. A board that allows every project of its Hub SHALL publish no project keys for that board. A board that allows some projects SHALL publish exactly those project keys and SHALL be able to publish an empty set, which states that the board accepts no new task. Project keys in the document are identifiers only. The document SHALL NOT contain project records, project paths, Git roots, default branches, tasks, notes, conversations, worktrees, Hub names, worktree base paths, or any other local setting. A board key SHALL be assigned when the board is first published, SHALL remain stable across board renames, and SHALL be unique within the document. A project key SHALL NOT be generated by publishing: a board SHALL publish the keys its projects already carry.

#### Scenario: Publish the board list
- **WHEN** the user publishes a Hub with two boards
- **THEN** the published document contains exactly those two boards in their board order
- **AND** each entry carries its key, name, and authored workflow YAML

#### Scenario: Exclude local data
- **WHEN** a Hub with projects, tasks, notes, and conversations is published
- **THEN** none of those records or their identifiers appear in the published document, except project keys named by a board's project keys

#### Scenario: A rename keeps the board key
- **WHEN** the user renames a published board and publishes the Hub
- **THEN** the published entry keeps its existing key
- **AND** only the displayed name changes

#### Scenario: Preserve authored workflow text
- **WHEN** the user publishes a workflow containing comments and custom formatting
- **THEN** the published workflow text matches the authored text without normalization

#### Scenario: Publish a board that allows some projects
- **WHEN** the user publishes a board restricted to two projects
- **THEN** that board's entry carries the two project keys
- **AND** no project path or project record appears in the document

#### Scenario: Publish a board that allows every project
- **WHEN** the user publishes a board with no project restriction
- **THEN** that board's entry carries no project keys

#### Scenario: Publish a closed board
- **WHEN** the user publishes a board restricted to no project
- **THEN** that board's entry states an empty project key set
- **AND** a receiving installation presents that board as closed for creation

### Requirement: Drafts and explicit publishing

Saving a board, a board name, a board order, or a workflow SHALL change local state only and SHALL mark that board as a draft or pending change. A storage that requires explicit publishing (Git) SHALL send every draft of the Hub as one document only when the user publishes. Publishing SHALL NOT be available while the Hub has unapplied team updates for that storage. When the published document changed since the last received document, a publish SHALL publish nothing, keep every local draft, and report the new team updates. A storage that supports continuous synchronization (Google Drive or a local folder) SHALL follow the Continuous synchronization requirement instead of an explicit publish action.

A board administration tool invoked at the user's explicit request SHALL publish the local board change when the Hub is bound and the comparison permits publishing, without a separate publish action. A storage that requires explicit publishing SHALL publish immediately after the local change, and a storage that supports continuous synchronization SHALL follow the Continuous synchronization requirement. This automatic publishing SHALL apply to board creation, board rename, workflow replacement, workflow edit, and team-scoped board removal, and SHALL NOT apply to a local-only board removal. A publishing failure or blocker SHALL keep the local change, keep the board as a draft or pending change, and report the failure.

#### Scenario: Saving a workflow creates a draft

- **WHEN** the user saves a workflow on a Git binding
- **THEN** the local board uses the new workflow
- **AND** the board is presented as a draft
- **AND** nothing is published

#### Scenario: Save and share publishes

- **WHEN** the user saves a workflow through the share action on a Git binding
- **THEN** the local save completes before the publish starts
- **AND** the published document contains the saved workflow
- **AND** the board is no longer a draft

#### Scenario: A failed share keeps the local save

- **WHEN** the local save succeeds and the publish fails
- **THEN** the local workflow remains saved
- **AND** the board remains a draft
- **AND** the failure is reported without discarding editing state

#### Scenario: Publishing is blocked by team updates

- **WHEN** the Hub has team updates that have not been applied
- **THEN** the Publish action is unavailable
- **AND** the interface presents Get updates as the required next action

#### Scenario: A lost publish race changes nothing

- **WHEN** the published document changed since the last check and the user publishes
- **THEN** nothing is published and every local draft is retained
- **AND** the Hub reports the new team updates

#### Scenario: Publish a board created through a tool

- **WHEN** an agent creates a board through a board administration tool on a Git binding and publishing is permitted
- **THEN** the board is saved locally before publishing starts
- **AND** the published document contains the new board
- **AND** the board is no longer presented as a draft

#### Scenario: Publish a tool workflow edit

- **WHEN** an agent replaces or edits a board workflow through a board administration tool on a Git binding and publishing is permitted
- **THEN** the local workflow is saved before publishing starts
- **AND** the published document contains the saved workflow

#### Scenario: Tool writes on continuous storage synchronize

- **WHEN** an agent changes a board through a board administration tool on a storage that synchronizes continuously
- **THEN** the local change is saved
- **AND** the change is left to the continuous synchronization rather than an explicit publish action

#### Scenario: A failed tool publish keeps the local change

- **WHEN** a board administration tool saves a local board change and the subsequent publish fails or is blocked
- **THEN** the local change remains saved
- **AND** the board remains a draft or pending change
- **AND** the failure is reported without discarding the local change

#### Scenario: Do not publish a local-only board removal

- **WHEN** an agent removes a team-bound board with the local-only scope
- **THEN** the board disappears locally
- **AND** no publish is started for that removal
- **AND** the team's document is unchanged

### Requirement: Team updates and three-way application

Applying team changes SHALL compare the published document with the last received document and the local Hub. Applying SHALL apply boards that changed only in the published document, SHALL keep boards that changed only locally as drafts or pending changes, and SHALL require an explicit per-board choice for a board that changed on both sides. A difference limited to layout SHALL NOT count as a change that requires a choice, where layout is stage placement, stage size, and connection layout: applying SHALL merge the layout of both sides per stage and per connection, SHALL apply the resulting workflow locally, and SHALL leave that board as a draft or pending change until it is published. When both sides changed the layout of the same stage, the local layout SHALL take precedence, and when both sides changed the layout of the same connection, the local connection layout SHALL take precedence. A difference in a board's project keys SHALL count as a change to that board, in the same way as a change to the workflow's meaning, and SHALL be applied, kept local, or resolved by the same per-board choice as the workflow. The merged workflow text SHALL preserve the authored text of the side that changed the workflow's meaning, and the local text when neither side did. A storage that requires an explicit operation (Git) SHALL apply the comparison when the user gets team updates. A storage that supports continuous synchronization (Google Drive or a local folder) SHALL apply the comparison automatically when it has no conflict, blocker, or local pending change on a board that also changed remotely, and SHALL require review otherwise. Applying SHALL be all-or-nothing for the Hub: either every selected change is applied or none is. After a successful application the last received document SHALL record the applied content, keeping the previous content for any board that still needs a choice.

#### Scenario: Apply a team-only change
- **WHEN** the team changed one board and the local installation did not change it
- **THEN** the board's published workflow is applied on the next get-updates or automatic synchronization
- **AND** the board is presented as up to date

#### Scenario: Apply a team-only change automatically
- **WHEN** a Google Drive or local folder check finds that only the team changed one board
- **THEN** that board's published workflow is applied during the check
- **AND** no user action is required

#### Scenario: Keep a local draft
- **WHEN** the local installation changed a board and the team did not
- **THEN** applying team updates leaves that board unchanged and it remains a draft or pending change

#### Scenario: Both sides changed the same board

- **WHEN** the team and the local installation both changed a board's workflow in ways that are not limited to layout
- **THEN** the review lists that board as needing a choice
- **AND** no part of that board is applied before the choice

#### Scenario: Choose the team version
- **WHEN** the user chooses the team version for a conflicting board
- **THEN** the board's published workflow is applied locally
- **AND** the local draft for that board is replaced

#### Scenario: Choose the local version
- **WHEN** the user chooses the local version for a conflicting board
- **THEN** the local workflow is retained as a draft or pending change
- **AND** the published workflow is not applied to that board

#### Scenario: Application is all-or-nothing
- **WHEN** applying an update set would be refused for any board
- **THEN** no board, workflow, or board order changes locally

#### Scenario: Apply a placement-only difference without a choice

- **WHEN** the team and the local installation changed only the layout of stages or connections on the same board
- **THEN** applying merges the layout without listing that board as needing a choice
- **AND** the board becomes a draft or pending change until it is published

#### Scenario: Keep the local placement beside a team workflow change

- **WHEN** the team changed a board's workflow meaning and the local installation only moved stages or adjusted connections
- **THEN** applying takes the team's workflow change
- **AND** the locally moved stages keep their placement and the locally adjusted connections keep their layout
- **AND** the board is not listed as needing a choice

#### Scenario: Keep the local placement for the same stage
- **WHEN** the team and the local installation moved the same stage to different positions
- **THEN** applying keeps the local position for that stage
- **AND** every other stage takes the position of the side that moved it

#### Scenario: Keep the local connection layout for the same connection

- **WHEN** the team and the local installation adjusted the same connection differently
- **THEN** applying keeps the local layout for that connection
- **AND** every other connection takes the layout of the side that adjusted it

#### Scenario: Merge different connections from both sides

- **WHEN** the local installation adjusted one connection and the team adjusted another connection of the same board
- **THEN** applying keeps both adjustments
- **AND** the board is not listed as needing a choice

#### Scenario: Preserve the authored workflow text

- **WHEN** applying merges an authored workflow with a layout-only difference
- **THEN** the merged workflow keeps the comments and formatting of the side that changed the workflow's meaning
- **AND** it keeps the local authored text when neither side changed the meaning

#### Scenario: Apply a team-only project scope change
- **WHEN** the team restricted a board's project scope and the local installation did not change that board
- **THEN** applying stores the team's project keys on that board
- **AND** the board presents that restriction

#### Scenario: Both sides changed the project scope
- **WHEN** the team and the local installation both changed the same board's project keys
- **THEN** the review lists that board as needing a choice
- **AND** choosing the team version applies the team's project keys with the team's workflow
- **AND** choosing the local version keeps the local project keys with the local workflow

#### Scenario: Keep the local scope beside a team workflow change
- **WHEN** the team changed a board's workflow meaning and only the local installation changed its project keys
- **THEN** applying the team's workflow requires the same per-board choice and does not apply the local scope as a team change
- **AND** the board remains a draft or pending change for the local scope

### Requirement: Refusal of destructive application

Get updates SHALL refuse the entire application and apply nothing when a workflow in the published document would leave an existing task in a column that the workflow does not define, or when a published board would collide with a local board that has not been published. The refusal SHALL name the blocking board, the missing column, and the number of affected tasks, and SHALL NOT offer an override action.

#### Scenario: Refuse a workflow that orphans task columns

- **WHEN** the published workflow removes a column that still holds local tasks
- **THEN** no update is applied
- **AND** the interface names the board, the missing column, and how many tasks block it

#### Scenario: Apply after the tasks move

- **WHEN** the user moves the affected tasks to a column defined by the published workflow and retries
- **THEN** the update set is applied

#### Scenario: Refuse a name collision with an unpublished board

- **WHEN** a published board has the same name as a local board that has not been published
- **THEN** no update is applied
- **AND** the interface explains that the local board must be renamed or published first

### Requirement: Board removal and orphan handling

When the team removes a board, the plugin SHALL remove it locally only when the board has no tasks and no unpublished changes. When the board has tasks or unpublished changes, the plugin SHALL keep it as an orphan: unbound from the published document, retaining its tasks, workflow, and drafts, and identified on its board tab. An orphan SHALL offer publishing as a new board with a new key and local deletion under the existing task rule. An orphan SHALL reconnect automatically when the team publishes a board whose key matches the orphan's last key, or whose name matches the orphan's last published name, and the local installation SHALL keep a single board for it.

#### Scenario: Remove an empty board

- **WHEN** the team removes a board that has no local tasks and no unpublished changes
- **THEN** the board is removed from the local Hub

#### Scenario: Keep a board that has tasks

- **WHEN** the team removes a board that still has local tasks
- **THEN** the board remains locally as an orphan
- **AND** its tasks, workflow, and conversations are unchanged

#### Scenario: Keep a board that has unpublished changes

- **WHEN** the team removes a board that has local unpublished changes and no tasks
- **THEN** the board remains locally as an orphan
- **AND** its unpublished changes are retained

#### Scenario: Identify an orphan on its tab

- **WHEN** a board is an orphan
- **THEN** its board tab presents an orphan state with an accessible label
- **AND** the state remains visible on an inactive board

#### Scenario: Publish an orphan as a new board

- **WHEN** the user publishes an orphan as a new board
- **THEN** the published document gains a board with a new key
- **AND** the local board is bound to that key

#### Scenario: Reconnect by key

- **WHEN** the team publishes a board whose key matches an orphan's last key
- **THEN** the orphan is bound to that entry
- **AND** no additional board is created

#### Scenario: Reconnect by name

- **WHEN** the team publishes a board whose name matches an orphan's last published name and no entry matches its last key
- **THEN** the orphan is bound to that entry
- **AND** no additional board is created

#### Scenario: Keep a single board after reconnection

- **WHEN** an orphan reconnects
- **THEN** the local Hub has the same number of boards as before the reconnection

### Requirement: Locally removed boards

When the user removes a published board only from this installation, the plugin SHALL record that board as locally removed, SHALL NOT apply that board from later team updates, and SHALL offer restoring it while the stored team document still contains it. A team-wide removal SHALL remove the board from the team document on the next synchronization: the next explicit publish for Git, or the next automatic synchronization for Google Drive. A team-wide removal SHALL NOT be recorded as locally removed.

#### Scenario: Remove a board only here

- **WHEN** the user removes a published board only from this installation
- **THEN** the board disappears locally
- **AND** the team document is unchanged
- **AND** later team updates do not recreate that board

#### Scenario: Restore a locally removed board

- **WHEN** the user restores a locally removed board that the team document still contains
- **THEN** the published workflow is applied locally again

#### Scenario: Publish a team-wide removal

- **WHEN** the user removes a published board for the team on a Git binding and later publishes
- **THEN** the board is absent from the published document

#### Scenario: Synchronize a team-wide removal

- **WHEN** the user removes a published board for the team on a Google Drive binding
- **THEN** the board is absent from the team document after the next successful synchronization

### Requirement: Automatic checks and published status

The host SHALL check each published Hub automatically at its configured interval. The default interval SHALL be five minutes for a Git binding and one minute for a Google Drive Cloud, Google Drive Local, or local folder binding, the minimum interval one minute, and a zero interval SHALL disable automatic checks while leaving manual refresh available. A check SHALL NOT start while a publish, synchronization, or update application for the same Hub is in progress. A check against Google Drive Cloud SHALL use the Drive change feed with a persisted cursor and SHALL read the document content only when the document revision changed; an expired or invalid cursor SHALL trigger a full document read. A check against a local folder or a Google Drive Local folder SHALL observe the document's last-modified time and size and SHALL read the document content only when either differs from the previous observation, when no previous observation exists, or when the observation cannot be read. A failed check SHALL NOT block local editing and SHALL be reported as unavailable together with the last successful check time. The host snapshot SHALL expose, per published Hub, the storage, the storage address, the synchronization mode, the publication status, the configured interval, the last successful check time, the current failure, the draft or pending count, the number of team changes a synchronization would apply, the conflict count, the per-board publishing state, and any review the storage itself requires.

#### Scenario: Default interval

- **WHEN** a Git-published Hub is configured without an interval
- **THEN** the host checks it every five minutes

#### Scenario: Default interval for Google Drive

- **WHEN** a Google Drive Cloud-published Hub is configured without an interval
- **THEN** the host checks it every minute

#### Scenario: Default interval for Google Drive Local

- **WHEN** a Google Drive Local-published Hub is configured without an interval
- **THEN** the host checks it every minute

#### Scenario: Default interval for a local folder

- **WHEN** a local-folder-published Hub is configured without an interval
- **THEN** the host checks it every minute

#### Scenario: Configured interval

- **WHEN** the user sets a fifteen-minute interval for a published Hub
- **THEN** the host checks that Hub every fifteen minutes
- **AND** other published Hubs keep their own intervals

#### Scenario: Disable automatic checks

- **WHEN** the user sets the interval to zero
- **THEN** the host performs no automatic check for that Hub
- **AND** manual refresh remains available

#### Scenario: A failed check does not block work

- **WHEN** a check fails because Google Drive Cloud, Google Drive Local, the repository, or the bound local folder is unreachable
- **THEN** local editing, saving, and task work remain available
- **AND** the Hub reports the failure and the last successful check time

#### Scenario: Status arrives with the snapshot

- **WHEN** a published Hub has available team updates, pending changes, or a storage-level review
- **THEN** the host snapshot reports the storage, synchronization mode, update count, pending count, review, and the per-board states
- **AND** the interface updates without an additional channel

#### Scenario: Checks do not overlap with changes in flight

- **WHEN** a check is due while a publish, synchronization, or update application for the same Hub is running
- **THEN** the check starts after that operation finishes

#### Scenario: Read content only when the document changed

- **WHEN** a Google Drive Cloud check finds no change to the document revision
- **THEN** the plugin does not read the document content

#### Scenario: Read the file only when its observation changed

- **WHEN** a local folder or Google Drive Local check finds that the document's last-modified time and size are unchanged
- **THEN** the plugin does not read the document content
- **AND** it does not reapply team updates

#### Scenario: Recover from an expired change cursor

- **WHEN** the stored Google Drive Cloud change cursor is rejected
- **THEN** the next check reads the document content in full
- **AND** the new cursor is stored after a successful read

### Requirement: Team Settings interface

Configuration SHALL include a **Team Settings** section for the active Hub. That section SHALL present the team storages as selectable cards, each with an icon, a name, and a one-line description — Git, Google Drive Cloud, Google Drive Local, and Local folder — and SHALL render the selected storage's surface. For a Git binding the section SHALL present the repository address, the check interval, the Hub status, the per-board states, the locally removed boards, and the actions Connect, Publish, Get updates, Refresh, and Disconnect. For a Google Drive Cloud binding the section SHALL present the connected account, the Drive and folder location, the synchronization status, the pending and conflict counts, the last successful synchronization, the current failure, the per-board states, the locally removed boards, and the actions Connect, Sync now, Review, Disconnect, and Switch account. For a Google Drive Local binding the section SHALL present the Google account and the folder location, the check interval, a **Choose folder** or **Change folder** action, the synchronization status, the pending and conflict counts, the last successful synchronization, the current failure, any storage-level review together with the step that clears it, the per-board states, the locally removed boards, and the actions Sync now and Disconnect. The Google Drive Local folder browser SHALL present the discovered accounts and locations, a breadcrumb of the current location, the folders of that location, a filter for that location, and the host's native folder picker as an alternative. When no Google Drive for desktop location is detected, or the platform does not support it, the section SHALL explain that condition, SHALL offer a rescan action together with the native folder picker, and SHALL NOT create a binding. For a local folder binding the section SHALL present the folder path, a folder selection surface that accepts a typed path or the host's folder picker, the suggested default folder, the check interval, the synchronization status, the pending and conflict counts, the last successful synchronization, the current failure, any storage-level review together with the step that clears it, the per-board states, the locally removed boards, and the actions Connect, Sync now, and Disconnect. A refused connection SHALL name the specific condition that prevented it. The storage cards SHALL change the rendered surface while the Hub has no binding and SHALL show the bound storage without changing it while the Hub is published; changing storage SHALL require Disconnect. The board SHALL present a banner when team changes are available or a review is required. The Hub tab SHALL indicate available team changes, pending changes, and conflicts without opening Configuration, and SHALL show them simultaneously when more than one applies. Each board tab SHALL indicate its own publishing state. A refusal SHALL present the blocking boards, columns, and task counts and SHALL NOT offer an override. The interface SHALL NOT require knowledge of revision-control concepts: it SHALL NOT present commit, branch, remote, fetch, or push wording.

#### Scenario: Open the Publishing section

- **WHEN** the user opens Team Settings for a Git-published Hub
- **THEN** the section presents the repository address, interval, Hub status, per-board states, locally removed boards, and the Git actions

#### Scenario: Open Team Settings for Google Drive

- **WHEN** the user opens Team Settings for a Google Drive Cloud-published Hub
- **THEN** the section presents the account, Drive and folder location, synchronization status, pending and conflict counts, last successful synchronization, current failure, per-board states, locally removed boards, and the Drive actions

#### Scenario: Open Team Settings for Google Drive Local

- **WHEN** the user opens Team Settings for a Google Drive Local-published Hub
- **THEN** the section presents the account, folder location, interval, synchronization status, pending and conflict counts, last successful synchronization, current failure, any storage-level review, per-board states, locally removed boards, and the Drive Local actions

#### Scenario: Open Team Settings for a local folder

- **WHEN** the user opens Team Settings for a local-folder-published Hub
- **THEN** the section presents the folder path, synchronization status, pending and conflict counts, last successful synchronization, current failure, any storage-level review, per-board states, locally removed boards, and the local folder actions

#### Scenario: Storage cards identify the storage

- **WHEN** the user opens Team Settings
- **THEN** each storage card presents an icon, a storage name, and a one-line description
- **AND** the selected card is distinguishable without opening it

#### Scenario: Select a storage while unpublished

- **WHEN** the Hub has no binding and the user selects one of the storage cards
- **THEN** the section renders that storage's connection surface
- **AND** no binding is created before the user connects

#### Scenario: Choose a folder with the folder picker

- **WHEN** the host provides a folder picker for a local folder binding and the user selects a directory
- **THEN** the chosen path fills the path field
- **AND** connecting uses that path
- **AND** typing a path remains available when the host provides no picker

#### Scenario: Browse for a Google Drive Local folder

- **WHEN** the user opens the Google Drive Local folder browser and navigates into a discovered location
- **THEN** the browser presents the folders of the current location and a breadcrumb of the path
- **AND** the user can select the current folder without typing a path
- **AND** the browser reports whether `kanban-hub.yaml` is already present there

#### Scenario: Use the native picker for Google Drive Local

- **WHEN** the user chooses the native folder picker instead of the browser
- **THEN** the selected folder is validated against the discovered Google Drive locations
- **AND** connecting uses that folder when it is inside a discovered location

#### Scenario: Google Drive Local is not available

- **WHEN** the Drive for desktop application is not detected or the platform does not support it
- **THEN** the section explains the condition and offers a rescan action
- **AND** it does not create a binding
- **AND** the native folder picker remains reachable

#### Scenario: Name the refused condition

- **WHEN** a local folder connection is refused because the path is missing, is not a folder, is not writable, is already in use, or is reserved
- **THEN** the section reports that specific condition
- **AND** it does not create a binding

#### Scenario: Name the refused Google Drive Local condition

- **WHEN** a Google Drive Local connection is refused because the folder is not inside a discovered location, the application is not detected, the location is unavailable, or the operating system denies access
- **THEN** the section reports that specific condition
- **AND** it does not create a binding

#### Scenario: The bound storage is not changed by the selector

- **WHEN** the Hub is published and the user opens the storage cards
- **THEN** the cards show the bound storage
- **AND** changing storage requires Disconnect

#### Scenario: Show a board banner

- **WHEN** the active board has team updates available or needs review
- **THEN** the board presents a banner that leads to Team Settings

#### Scenario: Indicate Hub publishing state on the Hub tab

- **WHEN** a published Hub has pending changes, team updates, or conflicts
- **THEN** its Hub tab indicates that state
- **AND** the indication is present while the Hub is not active

#### Scenario: Indicate board publishing state on the board tab

- **WHEN** a board is a draft, has team updates, needs a choice, or is an orphan
- **THEN** its board tab indicates that state with an accessible label

#### Scenario: Explain a refusal without an override

- **WHEN** an update application is refused
- **THEN** the interface names the blocking boards, columns, and task counts
- **AND** no override control is offered

#### Scenario: Avoid revision-control vocabulary

- **WHEN** Team Settings, the banner, or the indicators describe state and actions
- **THEN** they use storage or synchronization vocabulary rather than commit, branch, remote, fetch, or push wording

### Requirement: First connection

Connecting a storage that already contains a published document while the Hub has no received document SHALL present the differences and SHALL require choosing either to receive the published configuration or to publish the local one. Connecting a storage with no published document SHALL publish the local configuration without requiring that choice. A Git repository with no commits or no published document, a Google Drive folder with no `kanban-hub.yaml`, and a local folder with no `kanban-hub.yaml` SHALL all count as having no published document. ### Requirement: Storage-provider boundary

Access to the shared document SHALL go through a storage-provider boundary that reads a whole document with a version token and writes a whole document while the expected token matches. A provider that supports an atomic conditional write (Git) SHALL refuse a stale write without modifying the document. A provider that does not support an atomic conditional write (Google Drive Cloud, Google Drive Local, and a local folder) SHALL compare the token before writing, verify the written content after writing, and report a concurrent change without claiming an atomic guarantee; the previous content SHALL remain recoverable from the storage's own history or conflict copies. The supported storages SHALL be Git, Google Drive Cloud, Google Drive Local, and a local folder; any other storage SHALL be rejected with an explicit error. The document format, the merge rules, and the interface states SHALL NOT depend on the storage. Provider-specific connection, location, and synchronization state SHALL be exposed through the storage's own surface, and provider-specific connection rules SHALL be applied through the storage descriptor rather than by branching on the storage inside the publishing service.

When a Hub is bound to a storage that supports team files, the Team Settings section SHALL name the `team-files` directory of that binding and state that the team's documents in it are read and written by the agent tools. For a Hub bound to Google Drive Cloud, the section SHALL state that team files are unavailable with that storage and SHALL NOT offer a team file action. The section SHALL present no file browser, listing, or editor, SHALL NOT create or open the directory, and SHALL NOT add a client surface for team files.

#### Scenario: Name the team files directory

- **WHEN** the user opens Team Settings for a Hub bound to Git, a local folder, or a Google Drive Local folder
- **THEN** the section names the `team-files` directory and states that the agent tools read and write the team's documents there

#### Scenario: State unavailability for Google Drive Cloud

- **WHEN** the user opens Team Settings for a Hub bound to Google Drive Cloud
- **THEN** the section states that team files are unavailable with that storage
- **AND** no team file action is offered

#### Scenario: Do not add a file management surface

- **WHEN** the team files directory does not exist
- **THEN** Team Settings does not create it
- **AND** the section presents no file browser, listing, or editor
