# Spec Delta

## MODIFIED Requirements

### Requirement: Published document content
The published document SHALL contain a format version and one entry per board with a stable board key, the board name, the board order, the board's workflow YAML exactly as authored, and the board's project keys when the board allows only some projects. The format version SHALL be 2; a version 1 document SHALL be read and normalized as defined by Published document version negotiation. A board that allows every project of its Hub SHALL publish no project keys for that board. A board that allows some projects SHALL publish exactly those project keys and SHALL be able to publish an empty set, which states that the board accepts no new task. Project keys in the document are identifiers only. The document SHALL NOT contain project records, project paths, Git roots, default branches, tasks, notes, conversations, worktrees, Hub names, worktree base paths, or any other local setting. A board key SHALL be assigned when the board is first published, SHALL remain stable across board renames, and SHALL be unique within the document. A project key SHALL NOT be generated by publishing: a board SHALL publish the keys its projects already carry.

#### Scenario: Publish the board list
- **WHEN** the user publishes a Hub with two boards
- **THEN** the published document contains exactly those two boards in their board order
- **AND** each entry carries its key, name, and authored workflow YAML

#### Scenario: Exclude local data
- **WHEN** a Hub with projects, tasks, notes, and conversations is published
- **THEN** none of those records or their identifiers appear in the published document, except project keys named by a board's project keys

#### Scenario: A rename keeps the board key
- **WHEN** the user renames a published board and publishes the Hub
- **THEN** the published entry keeps its existing key
- **AND** only the displayed name changes

#### Scenario: Preserve authored workflow text
- **WHEN** the user publishes a workflow containing comments and custom formatting
- **THEN** the published workflow text matches the authored text without normalization

#### Scenario: Publish a board that allows some projects
- **WHEN** the user publishes a board restricted to two projects
- **THEN** that board's entry carries the two project keys
- **AND** no project path or project record appears in the document

#### Scenario: Publish a board that allows every project
- **WHEN** the user publishes a board with no project restriction
- **THEN** that board's entry carries no project keys

#### Scenario: Publish a closed board
- **WHEN** the user publishes a board restricted to no project
- **THEN** that board's entry states an empty project key set
- **AND** a receiving installation presents that board as closed for creation

### Requirement: Team updates and three-way application
Applying team changes SHALL compare the published document with the last received document and the local Hub. Applying SHALL apply boards that changed only in the published document, SHALL keep boards that changed only locally as drafts or pending changes, and SHALL require an explicit per-board choice for a board that changed on both sides. A difference limited to stage placement SHALL NOT count as a change that requires a choice: applying SHALL merge the placement of both sides per stage, SHALL apply the resulting workflow locally, and SHALL leave that board as a draft or pending change until it is published. When both sides changed the placement of the same stage, the local placement SHALL take precedence. A difference in a board's project keys SHALL count as a change to that board, in the same way as a change to the workflow's meaning, and SHALL be applied, kept local, or resolved by the same per-board choice as the workflow. The merged workflow text SHALL preserve the authored text of the side that changed the workflow's meaning, and the local text when neither side did. A storage that requires an explicit operation (Git) SHALL apply the comparison when the user gets team updates. A storage that supports continuous synchronization (Google Drive or a local folder) SHALL apply the comparison automatically when it has no conflict, blocker, or local pending change on a board that also changed remotely, and SHALL require review otherwise. Applying SHALL be all-or-nothing for the Hub: either every selected change is applied or none is. After a successful application the last received document SHALL record the applied content, keeping the previous content for any board that still needs a choice.

#### Scenario: Apply a team-only change
- **WHEN** the team changed one board and the local installation did not change it
- **THEN** the board's published workflow is applied on the next get-updates or automatic synchronization
- **AND** the board is presented as up to date

#### Scenario: Apply a team-only change automatically
- **WHEN** a Google Drive or local folder check finds that only the team changed one board
- **THEN** that board's published workflow is applied during the check
- **AND** no user action is required

#### Scenario: Keep a local draft
- **WHEN** the local installation changed a board and the team did not
- **THEN** applying team updates leaves that board unchanged and it remains a draft or pending change

#### Scenario: Both sides changed the same board
- **WHEN** the team and the local installation both changed a board's workflow in ways that are not limited to stage placement
- **THEN** the review lists that board as needing a choice
- **AND** no part of that board is applied before the choice

#### Scenario: Choose the team version
- **WHEN** the user chooses the team version for a conflicting board
- **THEN** the board's published workflow is applied locally
- **AND** the local draft for that board is replaced

#### Scenario: Choose the local version
- **WHEN** the user chooses the local version for a conflicting board
- **THEN** the local workflow is retained as a draft or pending change
- **AND** the published workflow is not applied to that board

#### Scenario: Application is all-or-nothing
- **WHEN** applying an update set would be refused for any board
- **THEN** no board, workflow, or board order changes locally

#### Scenario: Apply a placement-only difference without a choice
- **WHEN** the team and the local installation changed only the placement of stages on the same board
- **THEN** applying merges the placements without listing that board as needing a choice
- **AND** the board becomes a draft or pending change until it is published

#### Scenario: Keep the local placement beside a team workflow change
- **WHEN** the team changed a board's workflow meaning and the local installation only moved stages
- **THEN** applying takes the team's workflow change
- **AND** the locally moved stages keep their placement
- **AND** the board is not listed as needing a choice

#### Scenario: Keep the local placement for the same stage
- **WHEN** the team and the local installation moved the same stage to different positions
- **THEN** applying keeps the local position for that stage
- **AND** every other stage takes the position of the side that moved it

#### Scenario: Preserve the authored workflow text
- **WHEN** applying merges an authored workflow with a placement-only difference
- **THEN** the merged workflow keeps the comments and formatting of the side that changed the workflow's meaning
- **AND** it keeps the local authored text when neither side changed the meaning

#### Scenario: Apply a team-only project scope change
- **WHEN** the team restricted a board's project scope and the local installation did not change that board
- **THEN** applying stores the team's project keys on that board
- **AND** the board presents that restriction

#### Scenario: Both sides changed the project scope
- **WHEN** the team and the local installation both changed the same board's project keys
- **THEN** the review lists that board as needing a choice
- **AND** choosing the team version applies the team's project keys with the team's workflow
- **AND** choosing the local version keeps the local project keys with the local workflow

#### Scenario: Keep the local scope beside a team workflow change
- **WHEN** the team changed a board's workflow meaning and only the local installation changed its project keys
- **THEN** applying the team's workflow requires the same per-board choice and does not apply the local scope as a team change
- **AND** the board remains a draft or pending change for the local scope

## ADDED Requirements

### Requirement: Published document version negotiation
Reading a published document SHALL compare its format version with the versions this installation supports. A version 1 document SHALL be read and normalized to the current shape, with no project keys on any board, and SHALL NOT be rejected; the stored publishing state and the last received document SHALL be normalized the same way when they are loaded, so an installation that already published keeps its bindings, its orphan records, and its recorded removals. A document whose version is newer than this installation supports SHALL NOT be applied and SHALL NOT be published over, because its shape is unknown and writing it would drop content this installation cannot represent. In that state the installation SHALL keep its local edits, SHALL keep the Hub's publishing binding, and SHALL present a warning that the plugin must be updated. The warning SHALL be presented in the Team Settings panel and in the Hub's publishing status. The state SHALL clear without user action once a plugin that supports that version reads the document.

#### Scenario: Read a version 1 document
- **WHEN** the installation reads a published document written with format version 1
- **THEN** it reads the document as boards with no project keys
- **AND** no board is presented as restricted

#### Scenario: Normalize stored version 1 state
- **WHEN** the installation loads publishing state whose stored documents use format version 1
- **THEN** the state is normalized and retained
- **AND** its board bindings, orphan records, and recorded removals are kept

#### Scenario: Refuse to apply a newer document
- **WHEN** the installation reads a published document whose format version is newer than it supports
- **THEN** no team change is applied
- **AND** the local Hub is unchanged

#### Scenario: Refuse to publish over a newer document
- **WHEN** the published document uses a newer format version and the user asks to publish
- **THEN** nothing is written to the team storage
- **AND** the local change is kept as a draft

#### Scenario: Warn that the plugin must be updated
- **WHEN** the published document uses a newer format version
- **THEN** the Team Settings panel presents a warning that the plugin must be updated
- **AND** the Hub's publishing status presents the same state

#### Scenario: Clear the warning after an update
- **WHEN** a plugin that supports the published document's version reads it
- **THEN** the warning is no longer presented
- **AND** comparing and publishing proceed normally
