# Operations and Recovery

For the independent DSH **0.2.1-rc.2**–**0.2.2-rc.1** plugin. Start with [installation and usage](<../README.md>); this guide covers diagnostics, durable operations, policy boundaries, and acceptance evidence. It is not authorization to change the DSH core, profiles, permissions, signing, or authentication.

## Installation and update diagnostics

1. Use the required Node/pnpm versions from [the manifest](<../package.json>): runtime Node **>=20.19**, development helpers Node **22+**, and `pnpm@10.15.1`.
2. Install from the **repository URL** through the existing GUI → **Plugins → Add plugin**, using `https://github.com/filipeesch/deepseek-harness-kanban`. No build artifact is published, so the host resolves that address as a Git dependency and the profile builds it during installation: the first attempt is refused with `ERR_PNPM_GIT_DEP_PREPARE_NOT_ALLOWED` until the profile allows the manifest `prepare` build for the resolved commit, and the retry needs the profile's package manager on `PATH` plus registry access. The manifest version is bumped in the pull request that changes the artifact, so an installed copy reports which build it holds; pin a build with a committish on the same URL (`#<commit sha>`, or `#v<version>` for a tag that exists) when reproducibility matters, and never pin a branch. Use the absolute built package root and local `link:` specification only for a development checkout.
3. Update an installed plugin with `dsh plugin --profile <profile> update dsh-kanban`. A profile keeps the version it resolved, so adding the same address again does not refresh an existing copy. The command runs pnpm in `$DSH_HOME/profiles/<profile>` (by default `~/.dsh/profiles/<profile>`); the reserved `desktop` profile is managed by the Desktop-owned CLI.
4. Check the native installation result and plugin row. A fetched package, enabled flag, active host row, and working client page are distinct evidence. A native restart-required result is not a successfully applied hot reload. A successful installation does not certify that the bundle can activate; see [installation failure signatures](<operations.md#installation-failure-signatures>).
5. After a deliberate rebuild, explicitly reconcile the changed built files through native Plugin Manager, then refresh the **same existing GUI URL** and inspect it; see [the rebuild/reconcile procedure](<operations.md#explicit-reconciliation-after-a-rebuild>). Do not start a replacement server, edit a profile to force loading, or assume a source watcher exists. A browser refresh alone is not proof that a changed host module reloaded.

The currently exercised backend is `http://127.0.0.1:51781/`. Preserve your own existing host URL outside this environment. Neither a standalone Vite build nor another server updates that GUI.

### Installation failure signatures

**A package installed without built entries.** A Git-spec installation clones the repository, and a clone has no `lib/`, because that directory is build output ignored by Git. The host checks the bundle patch after `pnpm add` but not the package's public entry points, so the installation reports success and the failure only appears on the next start as an import error for `lib/index.js`; every relaunch repeats it until the profile is repaired. Do not read an applied installation as proof that the package can load. This is the ordinary result of an install whose build was never approved: allow the build for the resolved commit as described below, then reinstall.

**A stale profile override disables the Kanban row.** A user-layer `cordis.patch.yml` survives a plugin reinstall. An entry such as `- id: kanban` with `disabled: true` keeps the bundle off even when the package is installed and `dsh.profile.bundles` lists it, so the sidebar item never appears. Confirm the composed row before treating this as a build or activation failure:

```sh
dsh --profile <profile> --dump-config | grep -A2 'id: kanban'
```

If the row is disabled, enable Kanban in the plugin manager or remove that user-layer override, then restart the profile. Do not delete the profile or reinstall the package to fix a user-layer disable.

**Host packages shadowed by a plugin's own dependencies.** A profile installs with `nodeLinker: hoisted`, so a `@deepseek-ai` package installed transitively by another plugin lands at the profile root, and Node resolves that physical copy for every plugin row; the DSH installation is consulted only when the profile has no copy of that name. Two failure shapes follow. When the shadowed package is one the plugin imports at runtime, the import fails and the host reports that the bundle did not activate; a copy that predates the subpath the plugin needs fails with `ERR_PACKAGE_PATH_NOT_EXPORTED`, and a missing package or export fails with `ERR_MODULE_NOT_FOUND` or a missing named export. When the shadowed package participates in host services, DSH can instead report rows as incompatible with the running host and disable them, which surfaces as `startup failed` with required rows waiting for services. This plugin compiles the Typert protocol helper into its published entries and declares `engines.dsh`, so a stale `@deepseek-ai/dsh-typert-protocol` no longer breaks activation. Other SDK packages can still be shadowed: identify the culprit with `dsh plugin --profile <profile> why <package>`, inspect `$DSH_HOME/profiles/<profile>/node_modules/@deepseek-ai`, then update or remove the plugin that pins the older copy. A profile that shows hoisted `@deepseek-ai` copies under `node_modules` is presenting this failure mode.

**A Git install refused for build permission.** A Git-spec installation of a checkout that declares `prepare` fails with `ERR_PNPM_GIT_DEP_PREPARE_NOT_ALLOWED` until the profile permits that dependency's build scripts. The host restores the profile's `package.json` and `pnpm-lock.yaml` and keeps starting, but it offers no approval button for this refusal, because the guided retry is driven by a different pnpm report. Copy the exact key pnpm prints in the refusal into the profile's `pnpm-workspace.yaml` and retry. The key names the resolved commit and changes whenever the ref moves:

```yaml
allowBuilds:
  "dsh-kanban@git+https://github.com/filipeesch/deepseek-harness-kanban#<commit>": true
```

An approved run then runs the dependency's own install and build, which needs the profile's package manager on `PATH` plus registry access for the checkout's dependencies. The refused attempt is expected on a fresh profile, not a host defect: the guided retry is what records the approval.

### Network failure during a source installation

The recent source install failed on the default registry network path. An explicitly requested **one-shot** `https://registry.npmjs.org` override subsequently succeeded, without changing registry settings. Treat this as evidence about that attempt, not a universal registry diagnosis or permission to persist new settings.

Every install resolves the checkout's dependencies and the artifact's own runtime dependencies from the registry, so a restricted network can fail the install. Check the actual package-manager exit/application result. If an install times out, it may still be running: inspect current bundle inventory before retrying. Do not loop installs, silently change global registries, disable TLS checks, or treat a timeout as proof that nothing happened.

### Optional existing local Inspector helper

[The Inspector helper](<../scripts/dsh-inspect.mjs>) is optional and targets an **already-running local DSH Inspector**, default `http://127.0.0.1:9230`. Port 9230 is not the GUI port. The helper does not start an Inspector/browser/server, restart DSH, obtain authentication, edit profiles, or provide arbitrary evaluation verbs. Use it only when this current local Inspector is already available and you are authorized to inspect it.

Read-only examples, from the checkout with normal **Node 22+**:

```sh
node scripts/dsh-inspect.mjs --help
node scripts/dsh-inspect.mjs inventory --package dsh-kanban
node scripts/dsh-inspect.mjs clients
node scripts/dsh-inspect.mjs snapshot
# When multiple inspected Clients exist, select the source returned by clients:
node scripts/dsh-inspect.mjs snapshot --client SOURCE_ID
```

`inventory` returns projected public plugin/bundle status, not configuration secrets. `snapshot` distinguishes DSH's **Cordis semantic DOM** from the rendered browser DOM and returns text/value-free page structure only when a connected Client Inspector realm is available. Host-only semantic output is not visual GUI verification. No connected Client means no rendered-page evidence; do not improvise an auth-extraction or browser-attachment workaround.

The helper also has **explicit mutations**, never implicit fallbacks. Only an authorized operator choosing this alternative should run them; installation can fetch dependencies:

```sh
node scripts/dsh-inspect.mjs install --path /absolute/path/to/deepseek-harness-kanban --allow-mutation
# Enable is separate; installation deliberately starts disabled.
node scripts/dsh-inspect.mjs enable --path /absolute/path/to/deepseek-harness-kanban --allow-mutation
```

For the specific network failure above, the authorized one-shot install used:

```sh
node scripts/dsh-inspect.mjs install --path /absolute/path/to/deepseek-harness-kanban --allow-mutation --registry https://registry.npmjs.org
```

Before either mutation, the helper validates the built package's public entries and native bundle patch. It uses public plugin-manager operations, not direct profile edits. Helper exits are **0** for a successful result, **1** for a helper error, **2** for an application result other than applied, and **3** for restart-required. Inspect returned stage/application/error and package-manager exit data as well; do not report installation success from the outer exit code alone. A timed-out mutation includes a request identity and can remain in progress: inspect inventory before any retry.

[The separate live-verification helper](<../scripts/live-verify.mjs>) requires explicit owner-test authorization and can launch an ephemeral authenticated HTTP browser client of the existing backend. It is **not** an ordinary read-only Inspector command, not the original Desktop renderer, and not needed for installation. Do not invoke it without that authorization or capture/share secret-bearing login URLs, credentials, browser state, or native chat contents as evidence.

### Explicit reconciliation after a rebuild

On the inspected DSH **0.2.1-rc.2** host, the public `pluginManager.setBundleEnabled('dsh-kanban', true)` operation runs profile reconciliation **even when the bundle is already enabled**. Reconciliation detects changed loaded files in linked-package targets and can replace their host modules. This explicit operation does not require a root source watcher, compile source, or promise automatic source HMR.

After active task work/operations have settled, an authorized operator with the **existing local Inspector** can use the already-documented optional helper:

```sh
pnpm run build
node scripts/dsh-inspect.mjs enable --path /absolute/path/to/deepseek-harness-kanban --allow-mutation
node scripts/dsh-inspect.mjs inventory --package dsh-kanban
```

This calls the public manager method, not an internal reload hook. Read `application`, `restartReason`, errors, and active plugin state, then refresh **the same existing GUI URL** and verify the changed behavior. `changed: false` means the persisted selection did not change; it can legitimately accompany `application: applied` after reconciliation. Neither field alone proves the feature works. Honor `restart-required`; a failed replacement can leave the old plugin stopped, so do not assume stale code is still serving after an error.

Normal **Plugins disable/enable** remains a supported native lifecycle action, but switching off/on does not guarantee eviction of unchanged bundle modules. Do not call a nonexistent `hmr.reload`, private manager reload methods, or arbitrary Inspector evaluation to force a refresh. This procedure reconciles a **completed build**; it does not watch or rebuild the checkout for you. Actual own-bundle off/on and sidebar coexistence passed in the recorded ephemeral HTTP-client G1 run; the original Desktop renderer was not directly exercised.

### Historical exploratory helpers

The scripts under `scripts/verify-native-*` and the lifecycle helpers are optional, guarded historical experiments, not a required part of installation or product acceptance. Do not run them as routine diagnostics, enable consent flags automatically, replay DSH internals, or create native fixtures merely to satisfy a test count. The user-approved boundary is public-adapter/product contracts plus controlled Git and an existing-GUI smoke. Acceptance uses a deterministic, test-only model adapter; real-model requests are not part of it. Native activity and archive/history behavior remain upstream contracts; our coordinator still must respect those contracts and fail safely.

Old reports remain time-scoped and honest. The inconclusive schedule attempt was not qualified, its script was stopped with explicit user consent, and its fixture/base/archive/guard cleanup remains unverified. That does not authorize deleting user data or repairing DSH. Optional local artifacts remain ignored and are not published. See the [current evidence](<verification-preliminary.md>).

## Working directory and policy boundaries

A project may be Git-backed or a plain folder. Keep four paths distinct for a Git-backed project: **base project path**, **Git root**, **worktree root**, and **effective agent cwd**. For a Git-backed project the effective cwd is exposed only in the Git section's secondary details; the drawer header and Info do not repeat it. A folder project has no Git section and runs at its project path or retained checkout. For a base monorepo project `/repos/platform/services/api` in Git root `/repos/platform`, a worktree at `/worktrees/task-42` must contain `/worktrees/task-42/services/api`. A missing subdirectory is an error, not a reason to run at the checkout root.

New task conversations join a native workspace for their effective project or worktree path instead of being created with cwd only. The base workspace is shared; a worktree workspace belongs to its task and is removed with the task when no other session uses it. Task worktree and session-directory workspaces are registered hidden by default when the host exposes workspace visibility, while the shared base-project workspace stays visible. A pre-existing worktree workspace is hidden once when adopted; existing workspaces are not hidden retroactively, and a reader reveal is not undone by reconciliation. On the original DSH, the positional workspace API keeps every workspace visible. Existing conversations keep their creation-time workspace when the effective directory changes. Native `workingDirectory` changes preserve session IDs, prior histories, and immutable header cwd. The committed **effective cwd**, not the mere presence of a retained ready worktree binding, selects the active context: after an explicit return, chats and new tabs use base even if the old checkout remains bound. **Native Files and sandbox root stay at the original location**; neither a displayed cwd nor an attached checkout is an access grant.

Branching a retained task conversation adopts the fork as another conversation of that task. Adoption aligns the fork's effective directory to the task's before retaining it, retries briefly while the task has a pending context operation, and otherwise reports the failure and leaves the fork foreign; a fork of a subagent descendant or of a session no task retains is never adopted. The adopted conversation is owned by the task, so it counts toward and is archived by task deletion and no longer blocks shared-worktree cleanup. Because the native session header's cwd is immutable, a fork of a migrated conversation can join the task in Kanban but cannot be re-attached to the task's native workspace; only its effective directory is aligned for execution.

[The native adapter](<../src/host/native.ts>) resolves actual participant policies. Write preflight checks canonical paths against those policies; required Git commands use native confinement unless every participant already has an applicable full-access policy. It does not manufacture a union root, call idle GUI approval as a persistent grant, or auto-escalate/fall back to full access. Missing/incomplete confinement and incompatible participant policies fail visibly. Preflight is diagnostic, not a replacement for actual confinement or a race-free authorization guarantee.

Expected denials include read-only creation/removal and writes outside an original workspace root. Monorepo Git metadata can itself lie outside a subproject's permitted root even when its effective cwd exists. A prior successful Git create does not promise subsequent conversation access or future write permission.

[Task execution guards](<../src/index.ts>) validate the existing canonical expected and observed directories before send, at native pre-step, and at the public `llm/stream` boundary after request configuration and before the provider call. Native assembly/ensure can recover a missing cwd to its original directory; that recovery does not authorize task execution at the wrong root. A missing **active** tree/subdirectory/base or native context drift blocks execution; an inactive retained tree is not probed as if it were active. These are admission checks, not an atomic filesystem lease or permission grant.

Session history is read through the public `sessionQuery.observeSession` service; the adapter copies the immutable header, events, and inherited count and releases the observation lease. The `0.2.2` line also deprecates the callable return of `sessionProjections.register`, the registry-level `stateOf(session, key)`, and the `agent/request` waterfall. Do not reintroduce those APIs on a supported host: await the projection handle where the host exposes it, and use the `llm/stream` guard for request-era validation. Run the `@deprecated` sweep described in the project instructions when the supported DSH range changes.

When denied, keep the last committed context, inspect any partial progress, and choose an already-permitted destination or have the owner review native policy separately. Do not retry the denied operation unrestricted or rewrite session headers/permission roots. Returning to base can still need a functioning native adapter and accessible base directory; it is recovery, not a bypass.

## Failed or partial operations

[The coordinator](<../src/host/worktrees.ts>) journals requested intent, canonical target, prior per-session directories, completed switches, Git completion, archived session IDs, and failure details in durable task metadata. Git, native sessions, and metadata do **not** form one transaction. A failed response can follow a real external effect.

1. Open the affected card. The drawer-wide status above the tabs shows the operation kind, phase, target, and what completed. Do not infer that every tab moved from one successful switch or from the card's last committed cwd.
2. **Waiting** means all associated chats must become idle, including closed tabs and known turns, pending native interactions, jobs, descendants, and schedules. Waiting resumes on native activity events/startup; cleanup does not automatically cancel agents or owned work. Resolve the actual native activity deliberately, then use the kind-specific **Retry** action if needed.
3. During active context work, plugin admission of new chats/runs is gated and activity is rechecked before individual switches. Native actions can still race checks; there is no global idle lease. Do not send work into a mixed/unresolved context.
4. On **failed**, address the reported condition and choose the kind-specific **Retry** action to resume the recorded intent. Create recovery requires the persisted, operation-bound absent-target precondition plus the exact canonical repository/path/local-branch match; merely finding an existing matching checkout is not ownership proof. A preexisting destination is not adopted or blindly recreated: use explicit attach after reviewing it. A `SHARED_WORKTREE` failure offers the consented **Force remove checkout** action, which lists every blocking task and native conversation and removes the checkout after an explicit opt-in; it bypasses only the sharing guard. Policy denials, dirty-check discard consent, idleness, and the refusal to force while another task operates on the same checkout are never bypassed. Other failures are not instructions to broaden access.
5. Alternatively, **Return chats to project** cancels a pending confirmed transition and coordinates all retained conversations back to the exact base project path. This is **not rollback of external side effects**: it retains a verified created/attached checkout and binding for explicit later management while base becomes the active cwd; it does not delete the checkout or branch. A legacy/interrupted detached or mismatched-ref checkout can instead be recorded as diagnostic-only **Unclaimed worktrees**, without replacing a distinct known binding.
6. If native conversation archiving has begun during task deletion, Return is hidden or refused with `DELETE_IN_PROGRESS`. Use the deletion-specific **Retry deletion** action after resolving the failure. The plugin cannot silently unarchive chats or recreate a removed checkout.

**Unclaimed worktrees are read-only diagnostics**, never ownership, active context, or a removal target. The Git notice lists path/branch/reason with no automatic attach/remove or prefilled destructive target. Inspect with Git and choose a separate explicit attach if appropriate; successful attach clears the matching diagnostic. Task deletion leaves unclaimed checkout files on disk and warns about them.

**Branch modes:** discovery and Existing branch accept only supported local heads. A remote ref may be entered as the source of a New branch, which creates an attached local branch. Remote-only existing selections fail before checkout creation; do not retry them as if detached HEAD were supported existing-branch recovery.

Failed operations remain recorded for explicit recovery; nonfailed recorded work is reconsidered on restart. If a durable write itself failed, external state may be ahead of metadata. Preserve the error and inspect the known target before retrying; do not delete the journal or manually erase native logs to clear the UI.

### Card instructions, timed auto-run, and legacy transitions

The card **play** action and the timed send both use `task.runInstruction`. [The host command path](<../src/host/app.ts>) requires the task to still be in that stage, no unresolved context operation or confirmed transition, the exact unresolved entry identity (`expectedEnteredAt`), and an exact match with the expected raw instruction. A missing, replaced, or changed entry produces `INSTRUCTION_ALREADY_RESOLVED` or `INSTRUCTION_CHANGED`; review the current instruction rather than silently running a replacement. The host sends the instruction to the task's first open conversation — followed by the transition briefing when the stage configures two or more targets — creating one when none is open, after canonical context admission. It does not move the task, does not offer a conversation picker, and does not persist a confirmed transition. Admission failures surface inline on the card and in the drawer; inspect the conversation before retrying, because a retry is a new send.

### Auto mode and automatic advance

The card **Auto** chip and the drawer header chip both call `task.autoMode`. Enabling only persists the setting; it does not move the card or send a prompt. The host observes each task conversation's `turn/end`; when the reason is `completed`, no open conversation is running a turn, and the task owes the user nothing, it resolves the next stage and admits one durable pending transition with `origin: 'auto'`. A turn ends in the same advance for a task whose auto mode is disabled when it carries a declared transition for its current stage; that advance is admitted with `origin: 'agent'`. Both go through the one admission, so the pending-user-work hold, the destination re-resolution, and the atomic decision are identical.

Pending user work is one value composed once and read by the advance gate, the admission re-check, and the attention projection: an unanswered structured question round (the conversation-scoped `QuestionIndex`), an unanswered native question and any open approval (the live conversation-facts fold or the inspected log), and human prompts queued for a later turn (`agent.inbox` for a live conversation, the durable `inbox` projection otherwise; host-injected context notices parked in the steering list are not user work). Every conversation of the task counts, including one whose tab is closed. A prompt the host admitted itself is excluded by its `user-rpc` request identity, so a queued stage instruction is not user work. An unreadable conversation state is not idle: the read fails and the advance holds.

Pending user work is a hold, not a pause: nothing is admitted and nothing is recorded, the chip derives a held state that names what is missing, and the hold clears when the last item is consumed. Consumption alone does not move the card; the next completed turn re-evaluates it. The admission re-reads the same value immediately before it persists the transition, so a question admitted during the settle window cannot be bypassed.

The destination is the transition the task recorded for its current stage while that recording resolves; otherwise the first configured `allowed_transitions` entry, or the next stage in workflow order when the stage configures transitions but neither is recorded. A recorded destination is followed exactly: the task moves there and the crossing rule does not continue past it. On the default path, uninstructed stages are crossed toward the first instructed stage; when no reachable stage has an instruction, the task stops at the last reachable stage, and a visited stage is never revisited. The resolved destination and instruction are captured at admission, so a later workflow edit does not rewrite an admitted advance. Admission re-resolves the destination against the current workflow; if that destination changed or disappeared, the attempt records an `advance-failed` pause instead of moving the task to a stage the workflow no longer chooses, and a declaration that stopped resolving records `transition-stale` instead. Those diagnostic records exist only for a task whose auto mode is enabled: a task whose auto mode is disabled records no pause and stays in its stage, and its declaration waits for the next completed turn.

A declared transition is routing state that arms the turn, not a move: `set_next_transition` validates that the current stage configures transitions, that the target is one of them, and that a target is declared with a reason, and `list_allowed_transitions` returns the stage, the targets with their conditions, the default destination, and the current declaration with its reason. Neither tool moves the task, changes its position, sends a message, or changes auto mode during the call, and both work with auto mode off. `set_next_transition` acts only on the task that owns the calling conversation and rejects a task identifier; the read tool still resolves another task. A reason is required, trimmed, rejected when blank, and rejected rather than truncated when longer than the accepted limit; clearing the declaration needs no reason. The declaration is discarded whenever the task leaves the stage it was declared in, so only an editing workflow or a stale workflow edit can make it stop resolving. The drawer's next-stage action reads the same routing rule, so it follows a valid declaration, and refuses with the stale explanation when one no longer resolves. When the stage configures two or more targets, the host appends a briefing to the stage instruction it sends: each target with its condition, the current declaration, the default destination, and the `set_next_transition` call with its required reason. The briefing is derived at send time from the live workflow, so it cannot go stale against an edited workflow. When the advance consumed a declaration, the destination delivery is the instruction, then the reason block naming the stage the task left, then that briefing. A declaration stored without a reason, as an earlier release allowed, keeps its routing meaning and never arms an advance by itself.

Every other turn ending (`error`, `blocked`, `aborted`, `max-tokens`) records `autoMode.pause` with the matching reason and does not advance, for a task whose auto mode is enabled; a task whose auto mode is disabled records no pause and keeps its declaration for the next completed turn. An admission failure that happened before a durable transition records `advance-failed`. The pause is presented on the card and by the drawer's auto-mode chip, whose tooltip and accessible name carry the reason. It survives reloads and restarts and is cleared by an admitted advance, by disabling auto mode, or by any move of the task. Reading a conversation does not clear it. An admitted transition that fails is reported through the transition state, keeps auto mode enabled, and is not retried automatically. The destination entry stays unresolved, so the card play action remains available; sending that instruction clears the failed record, and the drawer also offers an explicit retry or a dismiss of the failed record. Any change to the setting forgets a turn that has not settled yet, so re-enabling or resuming within the settle window does not advance for a turn that ended before the change.

An agent can pause a task on purpose. `pause_task` records `autoMode.hold` with a reason the agent supplies; the reason is required, trimmed, and rejected rather than truncated when it exceeds the limit, so the card never presents a request the agent did not make. The pause suspends the advance while auto mode stays enabled, so the user's setting survives it, and it never moves the task, sends a message, clears the recording, or retracts an advance that was already admitted — an admitted transition still drains, and that placement keeps the pause. `resume_task` clears it together with any diagnostic pause without enabling a disabled task, moving the card, or advancing a turn that already ended. Movement also resumes it: a drop or drawer stage change clears both records, while the automatic advance's own placement clears only the diagnostic reason. Sending a prompt does not resume it. Activating the **Auto** chip resumes any recorded pause, for every reason, and turns the setting off only when nothing is recorded, which is why a recorded pause presents the chip as not pressed. The agent pause is a separate record from the diagnostic pause, so a turn that ends in `error` while the task is paused presents both reasons instead of replacing the agent's.

The record lives inside the task's auto-mode field of the local Hub document. Tasks are never published to a shared Hub document, so only this installation's own stored data can be affected: a plugin build older than this release rejects a stored Hub that contains a pause, so resume the task before downgrading.

The advance is host-owned and runs while the board is closed; it does not arm the five-second countdown and does not ask for a worktree choice. The host does not replay a turn that ended while it was not observing the conversations, but a pending transition that was already persisted is still drained on restart. Removing the destination from the workflow, or reaching a stage with no onward stage, leaves the card in place instead of sending to a missing stage; a recording that points at a removed target pauses auto mode with `transition-stale` until the card moves.

A move into an instructed stage starts one five-second, client-local countdown. The card's play slot becomes a cancel control with the remaining seconds, and the drawer shows the same notice above its panel in every section. Cancel removes the window only: the stage and position stay, the entry remains unresolved, and the card play action returns. The window is fixed at five seconds, is not persisted, and is not shared across tabs. It continues while the card is filtered, the Kanban panel is hidden, or another board or Hub is active. Reloading or restarting the plugin sends nothing and leaves the play action. A manual prompt, a new instructed entry, deletion, or any marker change cancels the window. A changed instruction is not a cancellation: the timer fires, admission rejects it, and the failure is shown with the play action restored. An unsent draft in the target conversation does not block the send and is left untouched.

The drawer shows waiting/sending/failed status above the tabs. Once context is ready, the kind-specific **Retry** action resumes the saved choice; **Return chats to project** clears it when prompt admission is not in progress. A stage may already have changed when native prompt admission fails, so check both stage and status rather than interpreting the error as a complete rollback.

The legacy confirmed-transition path still requires equality with the **exact raw instruction displayed for approval** before creating a new conversation, performing Git work, or journaling the move. A missing or changed instruction produces `INSTRUCTION_CHANGED`; review the current instruction rather than silently approving a replacement. Once admitted, the destination, chosen conversation, captured approved text, placement anchor, and stable native request ID are persisted; waiting or retry does not substitute a newer workflow instruction. A transition does not create or prompt for a worktree; use the notice or Git section instead. The notice's **Create worktree** uses the displayed derived branch, destination, and source directly; it refreshes collision-aware defaults when untouched, routes to Git when no destination is configured, and keeps a Git failure inline with a review path. **Move only** never submits a prompt. **Move and run** queues the instruction into only the selected native conversation; other chats are not messaged. The current UI does not create these legacy records.

The drawer stage control lists every workflow stage in workflow order. A permitted destination moves immediately. A destination the workflow does not permit is shown with lower visual emphasis but remains selectable; choosing it opens the same confirmation as a restricted board drop. Cancel leaves the task in place. If the host rejects the move, the dialog stays open with the problem and a retry that rechecks the current task and workflow; a changed source or missing destination is reported without a retry that cannot succeed. On admission, the host records a transient `transitionOverride` consent on the pending transition, so retry or restart completes the same confirmed move without changing the workflow. The native select popup may ignore the muted option color on macOS; the confirmation remains the functional guard.

For a permitted or confirmed instructed destination, the drawer arms the same five-second countdown and shows the notice in the current section; it never writes to the composer, and existing drafts or attachments stay untouched. Cancel removes the window and leaves the entry unresolved. The plugin does not use the native draft API for a stage change; a timed send is a normal host prompt admission, not a composer submission.

Every task conversation receives a native, model-facing task-context message before its first user message, once per conversation. The message contains the task title and ID, description, and workflow stage at first contact. It does not start a turn. The plugin presents it through a visible inline native Chat context row: a custom visible node claims the plugin-owned `kanban-task` message and delegates to the host's context-row renderer, so the row is part of the transcript flow and scrolls with it in the drawer and ordinary native Chat. It names `kanban-task` and reveals the full text on expansion. Later stage instructions contain only the instruction. New conversations get their own context; conversations whose first message already exists are not backfilled.

Legacy `PendingTransition` records remain readable and retryable in the drawer. Once legacy context is ready, **Retry confirmed action** resumes the saved choice; **Cancel action and return to base** clears it when prompt admission is not in progress. A stage may already have changed when native prompt admission fails, so check both stage and status rather than interpreting the error as a complete rollback. The current UI does not create these records.

For a legacy confirmed transition, an interrupted admission with `DELIVERY_UNCERTAIN` requires an explicit retry using the **same** native request identity; native deduplication protects that request. Admission uses native queue mode: it is not proof the turn started, finished, or succeeded. Do not manually send the legacy instruction again just because a waiting or uncertain status is visible, and do not change targets while admission is in progress.

Confirmed task deletions and worktree-only removals are admitted from persisted state only: the host verifies that the task exists, that its recorded worktree binding still matches the confirmed target, and that no other context operation holds it. Admission intentionally runs no Git command, native conversation read, or filesystem scan, so the command returns immediately and the board stays usable. Execution happens in a background lane per repository: at most one destructive operation runs in a repository, while operations on different repositories proceed concurrently. Each lane begins with the authoritative **preflight** — conversation idleness, canonical target stability, checkout sharing, and local-change detection — evaluated once per execution over the repository facts the operation resolved once. It then returns conversations to base, and from that point removes the checkout and archives native histories concurrently, so the card leaves the board only after both finish. The checkout removal re-evaluates the sharing refusal immediately before the Git command, because the host can report a new user of the checkout at any moment. The operation carries a persisted **queued** phase before execution. A preflight failure is recorded on the task with its failing phase and published to the card, the board notice, and the drawer status, where retry, return, force, and the separate discard consent recover it; a busy conversation moves the operation to **waiting** and it resumes on the next native activity event. The board notice also reports retained plain-checkout paths. A queued or in-progress operation resumes after a plugin restart, and shutting the plugin down does not discard its journal.

### Board default model

A board's workflow YAML may carry a root `model:` mapping (`provider`, `model`, and an optional `reasoning_effort`). **Configuration → Board** writes that mapping through a **Default model** picker — a closed control naming the current route that opens a searchable list of the host's providers and models, with the catalog reload inside it — and reports what the board holds now, including a non-dismissible readout when the saved route is no longer in the host catalog. The mapping is part of the workflow: it publishes with the board, is covered by `workflowMeaning` conflict detection, and is read back by `get_board_summary` with `include_workflow` as `defaultModel` (`null` when the board names none).

The choice is applied where a conversation is created, never where one already runs. `SessionModelPort.apply` answers with an outcome instead of throwing, and each caller decides what a refusal means: a schedule stays fail-closed and reports `SESSION_MODEL_UNAVAILABLE`, `SESSION_MODEL_FAILED`, or `SESSION_MODEL_SELECTION_UNSUPPORTED` before its prompt is admitted, while a board conversation fails open and is still created. A board default never blocks a move, a preparation, or a send.

When the route cannot be applied, the conversation runs on the deployment default and presents a dismissible notice naming the model the board asked for and the model in use. The outcome is reported once, on the receipt of the command that created the conversation: nothing is written to the task, the board, or the conversation, so the dismissal is view state only and the notice returns when the conversation is closed and reopened while the condition still holds. The first-execution preparation skips its native model step only when the board names a route the host offers; with no board default, an unknown route, or an unreadable catalog, the step is presented as before, so the person always sees the model when the board has not already chosen one.

Nothing here changes the installation-wide default model: the plugin applies a route to one conversation through the per-conversation selection interface and never through the command that saves the default. A schedule targets a project, never a board, so a schedule's own model stays independent of any board default.

## Session schedules

A Hub-scoped schedule runs a prompt unattended on a five-field cron expression with an explicit IANA time zone. Configuration lives in the Hub record and is validated by the same writer as every other Hub edit: an invalid expression, an unknown zone, a missing prompt, a project outside the Hub, and an expression that never fires are all refused at save time. The collection is optional, so a Hub stored before this capability loads unchanged.

The runtime is plugin-owned. A coordinator keeps one timer per enabled schedule and re-reads the stored schedules on every Hub change, so pausing, editing, or deleting a schedule takes effect immediately. A timer that fires late executes the occurrence it was armed for once and then recomputes the next occurrence strictly after the current time; occurrences that passed while no timer existed are never replayed. While a run of the same schedule is active, a due occurrence is dropped, not queued. Run-now shares the same admission set and refuses a paused or already-running schedule.

One occurrence resolves the schedule's project, uses that project's visible native workspace, creates a conversation (or reuses the continuous one), applies the stored model, sets the title best effort, sends the prompt, and records the outcome. It never creates or changes a task, board, workflow, note, or worktree. A relocating project is refused before any side effect. A reused continuous conversation is accepted only when its binding names the same project and its recorded directory passes `validateDirectory`; the project identity, relocation state, and directory are checked again immediately before the prompt. A failing occurrence is recorded as the last run and leaves the schedule enabled. Failures that happen before the prompt — a missing project directory, a workspace failure, an unavailable model — send nothing; a conversation already created for that occurrence is archived when it becomes idle.

Model application never writes the installation default. The host validates the route with `llm.resolveCallConfig`, checks catalog membership, resolves the live Agent, and installs the selection through the Agent's session-scoped model face (`agent.model.select`, public on DSH 0.2.2 and newer), which records it on the conversation only. When the host exposes no such face, the occurrence fails before sending and the failure is recorded; the plugin deliberately does not fall back to `sessionController.selectModel`, because that entry point also persists the installation default and its queued background write could overwrite a user's newer choice.

Conversations are archived only when genuinely idle: no running turn, no pending question or approval, no queued prompt, and no background job or subagent. The watcher reads the same question-aware facts as attention, so a conversation awaiting a plugin `decision_request` is never archived. An observation that arrives during an awaited evaluation marks the entry dirty and triggers a coalesced reevaluation, so the final idle event is not lost. A conversation that still needs the user stays visible and is archived after the turn that clears the interaction settles. Continuous conversations are never archived. A failed archive is recorded as `archiveError` on the run it belongs to (and ignored for an older conversation); the delivery outcome is unchanged. Archived conversations remain in session persistence and can be reopened from the schedule's last run, including a failed run.

Run state lives in its own storage domain, `kanban_schedule_runs`, keyed by schedule identity. It holds the in-flight marker (including the session as soon as one exists), the last run, and the continuous-session binding; it is never part of the Hub revision or the published team document. Admission reserves the in-memory slot synchronously, awaits the durable running marker before any native side effect, and rolls the reservation back if the write fails, so storage failure never produces an unrecorded execution. On startup a record whose run never finished becomes a failed run with `SCHEDULE_RUN_INTERRUPTED`, and records for schedules or Hubs that no longer exist are pruned. Deleting a schedule tombstones it in-process, so a late write from an in-flight occurrence cannot resurrect its runtime record.

Operational limits: 50 schedules per Hub, 120 characters per title, 20,000 characters per prompt. Deleting a schedule removes its runtime record and keeps the conversations it already created; deleting the last schedule removes the optional collection from the Hub, so an older strict schema can parse it. With schedules still stored, downgrading to a plugin release that predates this capability fails to parse the Hub; delete every schedule first. Shutdown aborts the plugin lifetime, stops timers, drains admitted executions before closing storage, and never creates or sends another occurrence after disposal; an already-admitted native turn may still finish.

Verification: `pnpm check` covers the cron evaluator (including daylight-saving gaps and overlaps, full-range day-field OR semantics, leap days, impossible dates, and the UTC or Area/Location zone contract), Hub validation and revision conflicts, durable admission with rollback, directory and relocation admission, session-only model application and fail-closed hosts, idle archiving with coalesced evaluation and recorded failures, commands, and the runtime projection. `pnpm test:browser --grep schedules` renders the list and editor with the host theme fixture, and `node scripts/e2e-dsh.mjs --checkout <checkout> --only schedules` exercises creation and one run against an isolated real composition.

## Archive, remove, and delete

| Action | Successful effect | Retained |
| --- | --- | --- |
| **Remove worktree** | Returns every retained chat to the base project, then removes only the eligible bound checkout. | Card, notes, native chats/histories, branch. |
| **Delete task** | Returns every retained chat to the base project; removes an eligible bound checkout; removes the owned worktree workspace registration; archives native chats; finally removes card/notes. A bulk selection closes its confirmation on accept, dispatches one background deletion per task, and reports no result dialog; a task that cannot be admitted becomes a board error and a later failure appears in the card status and notice. A plain checkout whose project has no Git root is never removed: its chats are archived in place and the result reports the retained path. | Native histories and Git branch; a plain checkout directory. |

For removal or deletion:

- Review the structured confirmation: task and project, conversation count and retained histories, exact worktree path, branch, whether the checkout was created by Kanban or attached externally, unclaimed checkouts, a running-conversation wait, and the separate local-changes consent. The confirmation stays open on failure with inline recovery. The command carries the expected target; a changed binding/canonical target requires new review instead of silently deleting a different directory.
- All associated conversations must be idle, including known native subagent descendants. A failed return to base preserves the checkout and recovery information; do not report deletion success. A later native unarchive must resume at the original project subdirectory, not a deleted worktree or the Git root. The plugin does not move or archive subagent child sessions individually; archiving the parent gates them natively.
- Modified tracked files **or untracked files** require the additional **Discard local worktree changes?** confirmation. **Keep local changes** preserves those files and checkout. Retry does not itself grant discard consent; when still required it presents that extra choice again.
- Refuse cleanup of a checkout shared with another task or a native session outside the task's conversation lineage. The task's own direct and nested native subagent descendants are owned, and a fork the task adopted is one of its retained conversations; a fork no task adopted and unrelated sessions are foreign. An already-absent checkout is treated as already removed, and its registration is removed without substituting a base project or Git root. The structured confirmation identifies an externally attached checkout and states that the checkout itself will be removed while its branch is kept; attachment does not establish exclusive ownership or permission to remove unrelated work. Registered-repository identity, safe canonical target, Git lock, policy, and checked Git exit results still apply.
- Unclaimed diagnostic checkouts are excluded from the expected destructive target and remain on disk even after task deletion.
- No associated worktree means **no filesystem cleanup substitute**. Never remove the base project, Git root, their ancestor, or Git metadata in place of a checkout. A branch is not deleted by either flow.
- Native chat archiving is **not history deletion**. No private native session log is directly unlinked. If cleanup/archive/storage fails halfway, retained associations and the journal support retry; do not claim completion until the remaining effects are accounted for.

These plugin behaviors are verified in controlled public native-port fixtures and real temporary repositories through [Git handling](<../src/host/git.ts>), [the coordinator](<../src/host/worktrees.ts>) and [host lifecycle commands](<../src/host/app.ts>). The host owns native archive/history implementation. If canonical native/shared-target metadata cannot be read, cleanup must fail closed: preserve the checkout, branch and recovery metadata and report the limitation. Do not skip a peer, inspect conversation content, repair native records or claim that physical cleanup succeeded in that host profile.

## Questions, notes, and stale views

- A `decision_request` page returns immediately. The form is optional text-composition UX, not a native pending-tool/approval interaction. Received pages can be answered while the round streams; a page that arrives while Additional Notes is open is announced with an action that opens it. Submit remains gated on actual native turn completion and valid answers, and the footer states that gate while the turn is still running. The tool's own description directs the agent to send every page the round needs and then always end its turn after the last page, and the per-call result repeats that short rule. Pressing Submit sends one ordinary question/answer message, removes the strip immediately, and restores the draft with the admission error if the send fails. Question rounds update through a conversation-scoped feed rather than the board snapshot, so turn completion, Submit confirmation, and ordinary-reply retirement do not wait for board attention projection.
- The expanded footer's **Dismiss** action removes every unresolved round in that conversation. An untouched round closes immediately; entered answers or notes show an inline discard confirmation first. Dismissal sends no conversation message, persists a dismissed-turn marker, prunes stored question-page payloads for those turns, and does not modify the native transcript. Reload, reconnect, and transcript replay do not restore the round; future rounds still appear. The awaiting-reply indication clears because the dismissed round is no longer pending.
- Closing submits no answer. A normal human reply retires the pending round; injected runtime-context records do not count as an answer. The transcript row stays silent and the strip is the only question surface. Canonical events reconstruct the round after reload, including PTC correlation; the in-memory submitted suppression is not promised durable. Unsent form drafts are durable per conversation: choices, Other text, per-answer notes, Additional Notes, and the active slide are stored in the `kanban_question_drafts` host domain, restored with the round baseline, discarded when the round is submitted, answered by an ordinary reply, or dismissed, bounded to the 100 most recently updated conversations, and removed together with the question projection when the owning task is deleted. The collapsed state stays a property of the open strip.
- A genuine native ask-user or permission request stays independent. Dismissing a rich form or sending its text does not settle an unrelated native pending interaction.
- Notes are shared by the task. Tags are normalized on write (trimmed, lowercase, 15 characters at most, four per note) and can be authored in the drawer or by the note tools; `list_notes` filters by any of the given tags and `update_note` accepts content, tags, or both. Tags stored before normalization are compared and displayed normalized and stay untouched until the user edits them. The Notes section filters by one tag at a time and edits in an overlay; note deletion is UI-only and the agent surface has no delete-note tool. Missing task context in an ordinary chat needs an explicit task ID, not a fallback to another task. There is no decision ledger or plugin TODO list.
- For feed errors use **Retry updates**; for initial board load use **Retry loading board**. Reopen a failed native tab or use its displayed retry action. A duplicate Kanban composer warning means close the other plugin view first, not copy the chat implementation.
- Creation commands return a **transient exact entity receipt** for that command; the UI does not infer a new project/task/tab/note by comparing snapshots. A missing receipt or unavailable created entity means inspect/refresh and select the saved entity explicitly before trying another creation. Receipts are not a persisted ledger or execution-success record. Project drafts/selection are locked during saves, and stale completion cannot rebind another draft.
- Workflow editing uses a code editor with line numbers, YAML highlighting, folding, search, live syntax/schema diagnostics, vertical resize, and a maximize toggle. Save is disabled while the document is invalid or still checking. The draft survives Configuration tabs; closing Configuration or reloading with a dirty draft asks first. Invalid workflow saves leave the last valid workflow intact; retaining referenced column IDs avoids orphaning active or pending-transition tasks.

## Team Settings recovery

A shared Hub keeps its state in the `kanban_sharing` storage domain. A Git binding also owns a managed clone under `DSH_HOME/kanban/shared/<hubId>`; a Google Drive binding owns provider state (`fileId`, `headRevisionId`, `changesPageToken`, `driveId`) and keeps the document in the selected Drive folder; a local folder binding owns the observation (`mtimeMs`, `size`) of the document it reads and keeps the document in the chosen directory, which a desktop client may synchronize. Google Drive tokens live in the host credential store (a 0600 file, not an OS keychain, readable by same-user processes). The OAuth callback uses a loopback port on the host, so the browser must run on the same machine as DSH; a remote browser cannot complete the connection. Only the local binding, the last received document, board keys, orphan records, provider state, and the last check result live there; the Hub aggregate and its schema are unchanged. Records written by the previous Git-only version are migrated to the storage-neutral shape at open.

- **Unreachable storage** is reported as `Updates unavailable` with the last successful check time. Local editing and task work continue; the next scheduled check retries. Git checks report their typed failure instead of hanging because terminal prompts are disabled for plugin-owned commands; Google Drive checks retry on the next interval and keep local changes pending.
- **A Git publish that loses a race** is refused with `SHARING_STALE_TOKEN`, publishes nothing, and refreshes the seen document so the interface shows the team updates. Run **Get updates**, resolve any review, then publish again.
- **A Google Drive or local folder write that loses a race** is detected before or after the write (`SHARING_STALE_TOKEN` or `SHARING_CONCURRENT_WRITE`), is not reported as success, and keeps local changes pending. Review the team changes; the previous document remains in the Drive revision history or in the desktop client's own history. Neither storage has an atomic conditional write, so the plugin never promises one.
- **A missing team document** is not treated as "the team removed every board". If the storage was readable before and `kanban-hub.yaml` disappears, the check reports `SHARING_DOCUMENT_MISSING` and leaves the local and received documents untouched.
- **A local folder is unavailable** is reported as `SHARING_FOLDER_MISSING`, `SHARING_FOLDER_NOT_DIRECTORY`, or `SHARING_FOLDER_UNWRITABLE` while local changes stay pending. Restore the folder — remount the drive, resume the desktop client, or fix the permissions — and the next check resumes without a new binding. The document is never recreated silently after it disappears.
- **A folder cannot be connected** names its condition: `SHARING_FOLDER_MISSING`, `SHARING_FOLDER_NOT_DIRECTORY`, `SHARING_FOLDER_UNWRITABLE`, `SHARING_FOLDER_RESERVED` for a directory inside the plugin's managed publishing workspace, or `SHARING_ADDRESS_IN_USE` for a folder another Hub already binds. Only the suggested `~/.dsh-kanban/<hubId>` path is created on connect; any other path is the user's to create.
- **A synchronization conflict copy** (`SHARING_CONFLICT_COPY`) is listed by name, blocks automatic apply and publish, and is never merged, renamed, deleted, or preferred. Decide which version is current, copy it over `kanban-hub.yaml`, remove or rename the other copies — Dropbox's `(conflicted copy)`, Drive's `(1)`, OneDrive's `-MACHINE` — and the next check clears the review.
- **A refused update** (`SHARING_REFUSED`) applies nothing. Resolve the named boards, columns, and tasks locally — move the tasks, rename the unpublished board, or delete the empty board — and run the sync again. The interface deliberately offers no override.
- **Authorization is lost or the account changes** (`SHARING_RECONNECT_REQUIRED`, `SHARING_AUTH_DENIED`, `SHARING_AUTH_POLICY`): reconnect the Google account. Local boards, workflows, and pending changes are kept; bindings that the new account cannot access are reported.
- **A corrupt sharing record** is quarantined with `SHARING_STORAGE_INVALID` and ignored at startup, so the Hub domain and the board keep working. Reconnecting the Hub recreates a clean record; local boards are untouched.
- **Disconnecting** removes the binding and any managed Git clone; reconnecting creates a new clone, rebinds a Drive folder, or binds the same local folder again. Deleting a published Hub removes its binding and managed workspace but leaves the team document, the bound local folder and every file in it, and the Google account authorization untouched. A plugin uninstall can leave a managed clone behind; it is safe to delete after confirming the Hub is no longer published in any installation.
- **Google Cloud prerequisites** are external: the OAuth client must be a Desktop app, the consent screen must include `openid`, `email`, `profile`, and `https://www.googleapis.com/auth/drive`, and a published External app needs Google's restricted-scope verification before accounts outside its test list can authorize. Testing mode limits refresh tokens to seven days. The default client id/no-secret exchange is only exercised by the manual acceptance run, not by CI.

**Rollback** to a plugin version that only understands the v1 sharing record presents migrated Git Hubs as unpublished (`SHARING_STORAGE_INVALID` on open). Every local board, workflow, task, and note is retained; reconnect the Hub to restore the binding from the team document. Disconnect Google Drive bindings before downgrading so the old version does not attempt to read Drive state. A local folder binding presents the same quarantine on a version that does not know the storage; the folder and its `kanban-hub.yaml` are untouched, so reconnecting on the newer version restores the binding.

## Metadata, disabling, and rollback

The plugin uses the native storage-domain service's namespaced **kanban**, version **1**, single-snapshot domain; see [the adapter](<../src/host/storage.ts>) and [validated durable store](<../src/domain/store.ts>). It stores projects/workflow/tasks/notes/operation references, not a second transcript database. Mutations are serialized, revision checked where supplied, and published after durable writes. One active host/profile writer is the supported boundary; there is no multi-host replication guarantee.

Use the correct host/profile's supported backup procedure before an upgrade or manual recovery, including both plugin metadata and native session storage as needed. The physical backing path belongs to that host configuration; do not guess it from cwd. This plugin provides no general backup/restore or export UI. Unsupported schema versions fail rather than silently reset; preserve the original snapshot and use compatible code or reviewed migration, not a blank-state overwrite.

Disabling/uninstalling through native plugin management removes plugin UI/tools/listeners and releases its UI session references. It does not mean delete tasks, native histories, branches, worktrees, or stored metadata. A compatible re-enable can reconnect the same native IDs. Reverting plugin code does not undo confirmed checkout deletion or native-chat archiving. Do not use source/core/profile edits to disguise partial cleanup.

## Build and test troubleshooting

Use a normal Node development installation, not the hardened executable embedded in the DSH app:

```sh
node --version
pnpm --version
pnpm run typecheck
pnpm test
pnpm run test:browser
pnpm run build
# Combined sequence: typechecks, tests, then build
pnpm run check
# Real-composition e2e is manual before release against an installed and built DSH checkout:
node scripts/e2e-dsh.mjs --checkout /path/to/deepseek-harness --check
node scripts/e2e-dsh.mjs --checkout /path/to/deepseek-harness
```

`pnpm run test:browser` is the separate Playwright harness for real CSS layout, CodeMirror, and animation behavior. It is intentionally not part of `pnpm run check`, which stays portable. `scripts/e2e-dsh.mjs` accepts any installed and built DSH checkout (it reports the checkout version and warns when it differs from the plugin's pinned SDK) and copies the plugin-owned scenario templates into that checkout's web test tree, runs them with `DSH_SNAPSHOT=replay`, and removes them afterward. The scenarios seed a question session without a model call and exercise real temporary Git for the worktree flow.

The hardened bundled Node failed loading the Rollup native addon due to a **Team ID/code-signing mismatch**. This does not justify disabling library validation, removing signatures/quarantine, or re-signing the app. Run the suite under normal Node instead and keep the actual failure distinct from test assertions.

Host and client native SDK augmentations belong to **separate TypeScript Programs**: [host typecheck](<../tsconfig.host.json>) and [client typecheck](<../tsconfig.client.json>). Declaration output is also separate via [host declarations](<../tsconfig.build.json>) and [client declarations](<../tsconfig.build.client.json>). [The build](<../scripts/build.mjs>) uses external native host packages and wraps the client bundle for DSH's browser module loader; it is not a standalone app. Do not fix augmentation conflicts by combining Programs or patching the installed SDK/core.
